## 三、技术方向分析与最优推荐

### A. 数据采集：最优方案是什么？

| 方案 | 可行性 | 数据完整度 | 实时性 | 维护成本 | 推荐 |
|---|---|---|---|---|---|
| 研招网爬虫 | 高（有反爬但可控） | 院校+专业+招生人数+考试科目 | 每年9-10月更新 | 中 | ✓ 优先 |
| 各校官网爬虫 | 低（格式各异） | 复试线+拟录取名单 | 每年3-4月更新 | 高 | ✗ 性价比低 |
| CSV 手动导入 | 高 | 用户自定义 | 随时 | 低 | ✓ 补充 |
| txkyer 种子导入 | 一次性 | 222校通信电子类 | 静态快照 | 零 | ✓ 初始 |
| 第三方 API | 无 | 无公开 API | - | - | ✗ 不存在 |

**最优推荐**：研招网爬虫（主数据源）+ CSV 导入（补充各校分数线/录取数据）+ txkyer 种子（初始启动数据）。不追求"实时"——考研数据每年更新一次，按招生季爬取即可。

### B. 前端图表：ECharts vs 替代方案

| 方案 | 功能 | 包体积 | 学习成本 | 推荐 |
|---|---|---|---|---|
| ECharts（当前） | 最全 | ~1MB（可优化到300KB） | 低 | ✓ 保持 |
| echarts/core 按需 | 同上 | ~300KB | 中 | ✓ 应优化 |
| Recharts | 中等 | ~200KB | 低 | ✗ 功能不够 |
| 自实现 SVG | 基础 | 0 | 高 | ✗ 无法满足 |

**最优推荐**：保持 ECharts，但改用 `echarts/core` 按需引入，可减重 70%。

### C. 数据库：SQLite vs 迁移

| 方案 | 读写并发 | 运维成本 | 数据量上限 | 推荐 |
|---|---|---|---|---|
| SQLite（当前） | WAL模式够用 | 零 | ~280TB | ✓ 个人使用保持 |
| PostgreSQL | 优秀 | 中 | 无限 | ✗ 过度工程 |
| MySQL | 优秀 | 中 | 无限 | ✗ 过度工程 |

**最优推荐**：保持 SQLite。个人使用场景下，WAL 模式的读写并发完全够用。大规模爬虫写入安排在低峰期即可。

### D. 择校推荐算法：当前 vs 增强

当前实现：分数线匹配（`score >= total_line`），按分差排序。

**增强建议（按优先级）**：
1. 加复录比排序权重（`retest_ratio < 1.5` 优先推荐）
2. 加录取均分匹配（`|score - admit_avg_score| < 20` 加分）
3. 加区域偏好（用户指定省份加权）
4. 加学科匹配（用户本科专业 → 对应学科代码筛选）
5. 可选：接入平台现有 AI 助手做自然语言择校问答
