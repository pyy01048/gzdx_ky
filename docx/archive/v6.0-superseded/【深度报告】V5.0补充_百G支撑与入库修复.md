# 第三部分 百G数据库支撑评估

## 3.1 你的实际情况

你已经有了 94.2GB 资料。这不是假设，是实测。所以真正的问题是：

**为什么 94GB 的资料，数据库只有 254MB？**

答案：因为 5309 个文件中只有 612 个被入库（来自 data/storage 目录），knowledge_base 目录里的 4697 个文件从未被处理。

## 3.2 如果全部入库会怎样

| 维度 | 当前 | 全部入库后（推算） |
|:---|:---|:---|
| 源文件 | 612 已入库 / 5309 总计 | 5309 全部入库 |
| 分块数 | 25770 | ~223,000（按 42块/文件 推算） |
| DB 文本+索引 | ~200MB | ~1.5GB |
| 向量（768维 f32） | ~75MB | ~650MB |
| DB 总大小 | 254.6MB | ~2.2GB |
| FTS 索引 | 25771 | ~223,000 |

**推算结论：100GB 资料全部入库后，DB 约 2-3GB。** 这远在 SQLite 能力范围内。

## 3.3 SQLite 能不能扛住

| 维度 | SQLite 能力 | 你的需求 | 结论 |
|:---|:---|:---|:---|
| 文件大小上限 | 280TB | ~3GB | ✅ 绰绰有余 |
| 行数上限 | 数十亿行 | ~22万行 | ✅ 绰绰有余 |
| 读写并发 | WAL 模式支持并发读 + 单写 | 个人使用，偶尔批量导入 | ✅ 够用 |
| 全文搜索(FTS5) | 百万级行正常 | 22万行 | ✅ 快 |
| 向量搜索(vec0) | 100万向量内正常 | 22万向量 | ✅ 快 |
| 批量导入性能 | 逐条插入慢，批量快 | 一次性导入 4697 文件 | ⚠️ 需分批 |

**结论：SQLite 完全能支撑你的百G场景。** 不需要迁移 PostgreSQL/MySQL。

## 3.4 但有三个前提条件

### 前提1：文件不要存进数据库

PDF/图片存为磁盘文件（你现在就是这样做的），数据库只存：
- 文件路径
- 解析后的文本
- 分块
- 向量
- 元数据

**你已经做对了这一步。** `documents` 表的 `file_path` 存路径，不存文件本身。

### 前提2：向量用 sqlite-vec 的 vec0 虚拟表

你现在用的就是 vec0 虚拟表（25770条向量），不是存为 BLOB。这是正确的做法。22万向量在 vec0 内查询时间 <50ms。

### 前提3：批量导入要分批 + 关闭自动提交

```python
# 正确的批量导入方式
db.execute("PRAGMA journal_mode=WAL")
db.execute("PRAGMA synchronous=NORMAL")  # 批量导入时用
db.execute("BEGIN TRANSACTION")
for file in files:
    ingest_file(file)  # 不要每条都 commit
db.execute("COMMIT")
```

# 第四部分 知识库自动入库诊断与修复

## 4.1 根因：路径错配

```python
# storage_watcher.py 第76行（当前）
STORAGE_ROOT = Path(__file__).parent.parent / "data" / "storage"
# 解析为: D:\平台\backend-main-fastapi\data\storage

# 应该改为
STORAGE_ROOT = Path(__file__).parent.parent.parent / "knowledge_base"
# 解析为: D:\平台\knowledge_base
```

**一行代码的修复，但你等了这么久都没发现，因为 manifest.json 是空的——没有可观测性。**

## 4.2 完整修复方案

### 修复1：路径对齐（storage_watcher.py）

```python
# 方案A：直接改路径
STORAGE_ROOT = Path(__file__).resolve().parent.parent.parent / "knowledge_base"

# 方案B：从配置读取（更灵活）
from models import PlatformConfig
def get_storage_root(db):
    cfg = db.query(PlatformConfig).filter_by(key="knowledge_base_path").first()
    if cfg and cfg.value:
        return Path(cfg.value)
    return Path(__file__).resolve().parent.parent.parent / "knowledge_base"
```

### 修复2：inbox 子目录自动监控

```python
# 在 storage_watcher.py 加 watchdog 监控
from watchdog.observers import Observer
from watchdog.events import FileSystemEventHandler

class InboxHandler(FileSystemEventHandler):
    def on_created(self, event):
        if not event.is_directory:
            # 新文件出现 → 入队 → 异步入库
            ingest_queue.put({
                "source": "watcher_inbox",
                "path": event.src_path,
            })

def start_watcher(path):
    observer = Observer()
    observer.schedule(InboxHandler(), path, recursive=True)
    observer.start()
```

### 修复3：manifest.json 填充

每次入库成功后，往 manifest 写一条：
```json
{"file_path": "真题/2026/数学/...", "doc_id": 1234, "chunks": 42, "status": "indexed", "ingested_at": "2026-10-08T20:00:00"}
```

### 修复4：统一入库队列（V4.0 第十部分提议的）

V4.0 已提出 `ingest_queue.py` + `ingest_logs` 表。这是正确的方向，但尚未实现。当前四个入库入口各自为政：

| 入口 | 代码位置 | 日志 |
|:---|:---|:---|
| 目录扫描 | storage_watcher.py | .processed_files.json |
| 单文件上传 | routers/storage.py | 无 |
| 网盘下载 | netdisk_service.py | netdisk_files表 |
| 一键修复 | kb_pipeline.py | 控制台输出 |

**统一为 `ingest_logs` 表后，能回答"这份资料入库了吗"这个关键问题。**
