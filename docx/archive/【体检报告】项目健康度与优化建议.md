## 二、🔴 高危问题（建议立即处理）

### 1. 真实密钥明文存放，且存在「废弃服务的密钥副本」
- `backend-main-fastapi/.env` 含**真实**百度网盘凭证：`BAIDU_NETDISK_APP_ID / APP_KEY / SECRET_KEY`。这是主后端实际读取的（代码 `main.py`、`netdisk_service.py` 用 `BAIDU_NETDISK_*` 读取，命名一致 ✅）。
- `frontend/server/.env` 含**同一套真实密钥**，额外还有 `BAIDU_SIGN_KEY`。但该 `frontend/server/` 服务在现行架构中已**不被使用**（见问题 2），属于冗余且危险的密钥副本。
- 当前靠 `.gitignore` 忽略 `.env` 未泄露到 git；但**若文件夹被压缩分享、云同步、或上传，密钥即明文外泄**。

**建议：**
- 立即确认该文件夹未通过任何渠道分享/上传；若已分享，去百度开放平台重置 AppKey/Secret/SignKey。
- 删除 `frontend/server/.env`（该服务废弃，密钥无需存在）。
- 密钥仅保留在 `backend-main-fastapi/.env` 单点；如确需多环境，使用 `.env.example` 占位、真实值走环境变量注入。

## 三、🟠 架构与一致性问题（建议近期处理）

### 2. `frontend/server/`（Node/Express BFF，端口 4001）是孤儿代码
- 架构演进后，Agent 能力已迁入**主后端** `backend-main-fastapi/routers/ai.py`（Python + CodeBuddy Agent SDK，端口 8000）。
- 证据：
  - `vite.config.js` 的 `/api` 代理指向 `http://127.0.0.1:8000`（FastAPI），**并未**指向 4001。
  - 前端源码（`frontend/src`）中**无任何**对 `4001` 或 `server/` 的引用；Agent 调用走 `utils/agent.js` → `${API}/agent/*`、`/api/chat`（即主后端）。
  - `package.json` 的 `npm run dev` 仍会 `tsx watch server/server.ts` 启动它，但启动后**没有任何请求路径使用它**。
- 该目录含 `server.ts / agent.ts / baidu.ts / config.ts / store.ts`，并持有真实密钥（`server/.env`）。

**建议：** 删除整个 `frontend/server/` 目录（含其 `.env`）。若有保留价值，至少移除 `.env` 并加 README 说明其已弃用。

### 3. `backend-agent`（端口 8003）是另一套重复 Agent 实现，未被前端调用
- 该目录是独立的 FastAPI 服务（`agent_core.py / llm.py / rag.py / tools.py / memory.py / model_manager.py`），提供 Ollama+RAG+工具调用的本地学习 Agent。
- 但前端 Agent 实际用的是主后端 `routers/ai.py`；前端源码无任何对 8003 的调用。`start-v2-full.bat` 却会启动它。

**建议：** 二选一——① 若计划启用，前端需新增对 8003 的调用/代理；② 否则删除或移入 `_legacy/`，避免在 `start-v2-full.bat` 中启动无用服务。

### 4. `backend-agent-proxy` 是空目录
- 大小为 0，无任何文件，所有启动脚本均未引用。

**建议：** 直接删除。

### 5. 启动脚本与文档相互割裂

## 四、🟡 运维与构建优化

### 6. 所有启动脚本将依赖装进全局 Python（无虚拟环境）
- `start.bat / start-v2.bat / start-v2-full.bat / start.ps1` 都用 `pip install -r requirements.txt --quiet`，安装到系统 Python；每次启动都重装（慢，且 `--quiet` 会掩盖安装失败）。

**建议：** 每个后端使用独立 venv（`python -m venv .venv` + `.venv\Scripts\pip install -r requirements.txt`），仅当依赖缺失时安装；或统一一个共享 venv。

### 7. 启动脚本过多且职责重叠
- 4 个脚本（`start.bat`=仅主服务；`start.ps1`=仅主服务；`start-v2.bat`=主+可选 OCR；`start-v2-full.bat`=主+可选 OCR+Agent）功能交叠、命名易混。

**建议：** 保留 1 个主入口（如 `start-v2-full.bat`），用参数/交互选项统一控制是否启动 OCR / Agent，废弃其余冗余脚本。

### 8. 前端源码与后端静态产物靠手动同步
- 前端构建产物在 `backend-main-fastapi/static/`（已 built），源码在 `frontend/src`。二者靠手动 `npm run build` 后复制，无自动化脚本/CI，容易出现「源码改了、线上静态没更新」的脱节。

**建议：** 增加构建脚本（build 后自动 `cp -r dist/* ../backend-main-fastapi/static/`），或引入简单的 monorepo/构建流水线。

### 9. 依赖版本策略不统一
- 主后端大多锁定（`fastapi==0.104.1` 等），但 `numpy / jieba / fastembed / ollama` 用 `>=`；OCR 与 Agent 后端**全部** `>=` 浮动版本，不利可复现与离线稳定。

**建议：** 统一锁版本或生成 `requirements.lock` / `pip-tools` 约束，保证「本地离线、一次装好长期可用」。
