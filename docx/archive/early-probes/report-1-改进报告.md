## 1. 执行摘要

### 1.1 一句话结论

**平台不是"界面丑"，是桌面端完全不可用—— 而且它自己不会报错。**

用户打开网站，左侧导航栏正常显示，右侧主内容区**一片空白**。内容其实渲染了，被一条 CSS 规则推到屏幕下方 900px 处，必须向下滚动才能看见。同时，**多处功能失效都是静默的**：组件签名与调用方不匹配导致"暂无数据"提示渲染成空白卡片、前端store 键名读写不一致导致后端状态指示器永远不亮、13 处 `catch(() => {})` 吞掉所有错误、后端状态挂了也没有任何提示。

**这些都不会在控制台报错，只会静默地让用户面对空白。这才是"界面有极大问题"的真实成因，不是视觉设计。**

### 1.2 现状：平台能做什么、不能做什么

**能做的（实测确认）**：

- 构建健康：`npm run build` 退出码 0，1089 模块 / 37 chunk，耗时 7.71 秒
- 测试真实在跑：61 个用例 / 61 通过 / 0 失败，耗时 21 秒
- 移动端（≤860px）**完全正常**：顶栏、面包屑、底部导航、统计卡、任务列表全部正确渲染
- 平板（768px）**完全正常**：倒计时 442 天、目标院校、任务卡完整显示
- 后端 8000 端口在线，`/docs` 返回 200，31 个 router 正常注册
- 知识库真实可用：1846 份文档、27893 个知识分块、25815 条向量

**不能做的（实测确认）**：

- ❌ **桌面端（>860px）所有页面首屏全白** —— 影响全部 28 个路由
- ❌ **手机上进择校模块后出不来** —— 12 个子页是单向门
- ❌ **单词列表永远加载失败** —— 前端硬编码 `page_size:2000`，后端上限 500，必然 422
- ❌ **AI 助手整条链路是死代码** —— 前端 9 个端点，后端 0 实现
- ❌ **桌面端进不了设置页/题库/分数分析** —— 3 个孤儿路由
- ❌ **16 处"暂无数据"提示渲染成空白卡片**

### 2.2 双轨方法：静态普查 + 浏览器实测

本轮采用**双轨并行**的诊断方式，这不是冗余，而是因为两种方法各有明确的盲区，且**盲区恰好互补**。

| | 静态普查 | 浏览器实测 |
|---|---|---|
| 执行者 | 调查员 | 验证员 |
| 方法 | 全文件通读 + grep/glob/脚本实测计数 | Playwright + Chrome 155 直驱 |
| 能发现 | 代码里的结构问题、跨文件不一致、死代码、契约不匹配 | 渲染位置、视觉呈现、控制台错误、网络失败 |
| **盲区** | **看不见 CSS 级联结果** | **看不见代码全貌**，只能看到渲染结果 |
| 典型盲区实例 | ❌ **漏检了 P0-0 桌面白屏** | ❌ 不知道`<Empty>` 组件签名的意图 |

#### 静态普查的固有盲区（本轮最重要的方法论收获）

静态普查能核对"`.mobile-top` 在 `@media` 内有没有定义"，却**无法核对"媒体查询外有没有基准隐藏"**。

原因是：CSS 的 `@media` 规则是**增量覆盖**，不是**条件定义**。一个元素如果在媒体查询外没有基准样式，浏览器就会用默认值（`<header>` 的默认值是 `display:block`）—— 这是一个**关于"未定义"的行为**，静态阅读天然不警觉。

**这类缺陷只能靠实际渲染几何发现。** 本报告的 P0-0 正是由实测发现的，静态方在 528 行报告中完全漏掉了它。

#### 运行时实测的补充价值

实测不只是"看一眼好看不好看"，而是采集三类可量化的数据：

- **像素级**：截图 MD5 —— 不同页面截图完全相同，说明渲染结果完全一致（都是空白）
- **几何级**：`boundingBox` —— 元素在视口中的真实坐标与尺寸
- **运行时级**：DOM 快照 + `textLen` —— 节点是否存在、里面有没有文字

本报告的每个 P0 至少有其中两级证据。

### 2.4 交叉验证机制（为什么不能只信一份报告）

本轮采用三方协作：调查员（静态普查）→ 验证员（运行时取证）→ 审查员（交叉裁决）。

**三方交叉产出了单看任一份报告都得不到的结论。** 最典型的一例是"测试用例数"：

| 来源 | 结论 | 对错 |
|---|---|---|
| 调查员（静态） | "3 passed" | ❌ 引自过期日志 |
| 验证员（首轮实测） | "3/3 通过" | ✅ 在其实验时点准确无误 |
| **审查员（磁盘枚举）** | **磁盘上有 4 个测试文件、48 个 `it()` 声明；验证员的测试日志时间戳早于其中 3 个文件的创建时间** | ✅ **唯一正确** |

**如果只有静态方，会得出"前端只有 3 个测试"的错误结论；如果只有实测方，会永久错过那 3 个文件的存在。** 这个结论对后续"61 个用例为什么仍漏掉整个 P0"的分析至关重要 —— 它揭示了测试文件是在诊断期间由计划外进程写入的（详见 §6.1）。

#### 裁决规则

交叉裁决遵循三条规则，避免"各执一词"：

1. **静态说有、实测说没有** → 以实测为准，但必须复核根因（例：kaoyan 是否死胡同）
2. **实测没测到、静态说有** → 以静态为准，但必须逐行回核源码（例：`/settings` 桌面无入口）
3. **两份都错** → 重新枚举磁盘（例：测试用例数）

### 4.1 P0-0 桌面端全站白屏

#### ① 现象

用户打开网站，**左侧导航栏正常显示，右侧主内容区一片空白**。

内容其实**已经渲染了** —— DOM 里有582 个字符的文本，统计卡、任务列表、图表数据全都在。但它们被推到屏幕下方 900px 处，**用户必须向下滚动一整屏才能看到任何内容**。而首屏—— 用户打开网站第一眼看到的那一屏 —— 只有左上角的"考研档案/ 倒计时 442 天"和左边的导航栏。

讽刺的是，这条"考研档案 倒计时 442 天"的横条，本该是**只在手机上显示的移动端顶栏**。

#### ② 复现

```
视口宽度：1440 × 900（任意 > 860px 的宽度）
路由：任意（实测 28 个路由全部如此）
步骤：
  1. 启动前端 dev server
  2. 浏览器宽度设为 1440px
  3. 打开 http://127.0.0.1:5173/#/  （或任意其他路由）
  4. 观察首屏
预期：看到 Dashboard 的 Hero、统计卡、图表
实际：主内容区完全空白
对比：把浏览器宽度改为 375px 或 768px，同样页面完全正常
```

**注意这是桌面端独有的问题。** 如果验证者的窗口不够宽，可能会误判为"没问题"。

#### ③ 根因机理

**这是本报告最重要的一段。** 缺陷是四步因果链，每一步都必须成立才会出现白屏：

**第 1 步：`.app-shell` 是一个两列 CSS Grid，且没有指定子项位置**

```css
/* global.css:127-131 */
.app-shell {
  display: grid;
  grid-template-columns: 248px 1fr;
  min-height: 100%;
}
```

关键：**没有 `grid-template-areas`，也没有给子项指定 `grid-column` / `grid-row`。** 这意味着浏览器会按**源码顺序自动填充**网格。

**第 2 步：`.mobile-top` 是 `<header>`，且无条件渲染**

```jsx
/* Layout.jsx:183-234 —— .app-shell 的子元素顺序 */
<aside className="sidebar">...</aside>
<header className="mobile-top">...</header>
<main>...</main>
```

`.mobile-top`（移动端顶栏）在 JSX 里是**无条件渲染**的 —— 不像 `.bottom-nav` 那样由 CSS 控制显隐。

**第 3 步：`global.css` 里`.mobile-top` 全局只有一条定义，且在媒体查询内**

```css
/* global.css:541 */
@media (max-width: 860px) {
  .mobile-top { display: flex; align-items: center; }
}
```

这是**全项目唯一的 `.mobile-top` 规则**（grep 确认）。它写在 `@media(max-width:860px)` **内部**，只在窄屏生效。

**第 4 步：桌面端没有任何样式约束 `<header>` → 浏览器用默认值 `display:block`**

`<header>` 是块级元素，浏览器默认给它 `display:block`。因为媒体查询外的基准样式缺失，桌面端的 `.mobile-top` 就是一块普通的块级元素。

**四步叠加的结果：**

```
.app-shell 的两列 grid： [ 列1: 248px ] [ 列2: 1fr=1192px ]

自动填充过程：
  第 1 个子项 aside.sidebar     → (行1, 列1)  248 × 900   ✓ 正常
  第 2 个子项 header.mobile-top → (行1, 列2)  1192 × 900  ✗ 抢占整块内容区

  .bottom-nav   w=0 h=0  display=none✓ 正确

**`main` 的 y=900 恰好等于视口高度（900）** —— 这意味着用户向下滚动**恰好一屏**才会看到内容。在"用户打开网站第一眼"这个场景里，等于白屏。

#### ④ 对照证明：这不是设计意图，是一个单点遗漏

同一个文件里的 `.bottom-nav` 是**同类组件**（移动端专属UI），它就写了基准样式：

```css
/* global.css:1530-1531 —— .bottom-nav 的正确写法 */
.bottom-nav { display: none; }   /* ← 基准隐藏 */
```

然后在 `@media(max-width:860px)` 内再打开：

```css
@media (max-width: 860px) {
  .bottom-nav { display: flex; ... }
}
```

**同一类组件，一个写了基准、一个漏了。** 这说明：
- `.mobile-top` 显示为移动端专属顶栏是**明确的设计意图**（否则不需要它在窄屏有 `display:flex`）
- 但添加基准 `display:none` 这一步**被遗漏了**
- 这是**移动优先改造时的单点遗漏，不是设计决策**

**再一个佐证**：`mobile-first` 改造的痕迹在代码里非常明显 —— `global.css:1551-1554` 有一组针对 `≤380px` 的压缩规则（`min-width:0; padding:4px 2px; font-size:9.5px`），这是典型的移动端适配。**但适配窄屏时，加了新的窄屏规则，忘了给旧的桌面基准补上对应的隐藏规则。**

>

>
> **Q3：改动量？**
> **6 行 CSS，1 个文件。** 这是全报告投入产出比最高的一项。

### 4.2 P0-1 空状态提示渲染为空白块

> ### ⚠️ 措辞澄清（请勿误读为整页崩溃）
>
> P0-1 是**局部失效，不是整页白屏**。
>
> 实测 `/quiz-section` 整页 `mainTextLen=2206`，统计卡完全正常（1871 题 / 12 错 / 12 待 / 0 毕），**只有"数字电子技术 · 章节分段"那一个卡片是空白的**。
>
> "16 处空状态空白"指的是 **16 处"暂无数据"提示**，不是 16 个页面整体崩溃。**本节写作与后续修复都必须保持这个准确表述。**

#### ① 现象

用户在某些页面会看到一个**纯白色空卡片** —— 卡片有大小（约 305×96），但里面**一个字都没有**。

用户会困惑："这是加载中？还是没有数据？还是我操作错了？"

**而本该出现的提示文字（如"暂无题目，请先导入题库"）确实写在了代码里，只是 React 把它丢弃了。**

#### ② 复现

```
视口宽度：375 × 812（⚠️ 必须用移动端宽度，桌面端拍不到，见下方取证陷阱）
路由：/#/quiz-section
步骤：
  1. 打开 /#/quiz-section
  2. 向下滚动到"科目分项"区域
  3. 观察"数字电子技术 · 章节分段"卡片
预期：显示"暂无题目"图标 + 标题 + 说明文字
实际：纯空白卡片，容器 305×96，零可见文字

对照：/#/quiz-bank 同一位置的空状态正常显示
排除：/#/quiz 页无空状态，页面正常 → 排除"整个 quiz 模块坏了"
```

#### ③ 根因机理

**三处失配叠加，形成"三重空白"。**

**第一重：组件签名不接收调用方传的 prop**

```jsx
/* UI.jsx:64 —— 组件签名 */
export function Empty({ icon, title, desc, action }) {
```

但 6 处调用方传的是 `text`：

| 调用位置 | 传入的 prop |
|---|---|
| `QuizSection.jsx:120` | `text="暂无题目，请先导入题库"` |
| `QuizSection.jsx:143` | `text="暂无薄弱点"` |
| `QuizSection.jsx:165` | `text="暂无错因分析"` |
| `QuizSection.jsx:181` | `text="暂无待复习内容"` |
| `QuizSection.jsx:199` | `text="暂无讲义"` |
| `Analysis.jsx:240` | `text=...` |

**JavaScript 不会报错** —— 给函数传一个它没声明的参数是完全合法的，函数内部该参数是 `undefined`。

所以：`icon` = undefined、`title` = undefined、`desc` = undefined。React渲染成空节点。

**第二重：图标类名全项目未定义**

```jsx
/* UI.jsx:67 —— 用了 .es-ico */
<div className="es-ico">{icon}</div>
```

而 `global.css:1000` 定义的**真实类名**是 `.empty-state-icon`：

```css
/* global.css:996-1003 —— 真实类名 */
.empty-state-icon { ... }
.empty-state-title { ... }
.empty-state-desc  { ... }
```

**`.es-ico` 在全项目 CSS 里 0 处定义**（与 `v2-design.css:312` 的 `.res-ico` 字母相近但不是同一个类）。

**第三重：裸标签没挂类**

```jsx
/* UI.jsx:68-69 —— 裸 <b> 和 <span> */
<b>{title}</b><span>{desc}</span>
```

没有 `className="empty-state-title"` / `empty-state-desc` → 即使有文字，**字号、颜色、行高、间距全部失效**（浏览器默认样式）。

**三处叠加的效果：**

| 元素 | 本应 | 实际 |
|---|---|---|
| 图标容器 | 显示空状态图标 | `.es-ico` 无样式 → 尺寸为 0 |
| 标题 | "暂无题目" 17px/600 | `undefined` → `<b></b>` 空标签 |
| 描述 | 灰化说明文字 | `undefined` → `<span></span>` 空标签 |
| 容器 | 305×96 有内容 | 305×96 **完全空白** |

**加剧因素：两套空状态样式并存**

```css
/* v2-design.css:558-562 */
.empty { ... padding: 28px 24px; }

/* global.css:996-1003 */
.empty-state { ... padding: 36px 20px; }
```

两套样式**padding 相差 8px**，且类名不同（`.empty` vs `.empty-state`）。`Empty` 组件挂的是 global 那套，但开发者可能以为 v2 那套才是当前的 —— 这种混淆加剧了排查难度。

#### ④ 因果链已闭合（同组件、同 CSS、仅 props 不同）

这是本缺陷能定性为"已实测证实"而非"静态推导"的关键证据：

| 路由 | `.empty-state` 存在 | `<b>` 实际文本 | `<span>` 实际文本 | textLen | 判定 |
|---|---|---|---|---:|---|
| **`/quiz-section`** | ✅ | **`""`（空）** | **`""`（空）** | **0** | ❌ 空白块 |
| `/quiz-bank` | ✅ | `"暂无题目"` | `"点击上方「刷题中心」做题，或从文档中提取题目"` | 27 | ✅ 正常（对照组） |
| `/quiz` | ❌ 无 | — | — | — | ✅ 正常（第二对照） |

**决定性证据 —— `/quiz-section` 的 DOM 快照原文：**

```html
<div class="empty-state">
  <div class="es-ico"></div><b></b><span></span>
</div>
```

写进去的 `"暂无题目，请先导入题库"` **被 React 直接丢弃**。

**对照 `/quiz-bank`（正确传 `title/desc`）：**

```html
<div class="es-ico"><svg .../></div>
<b>暂无题目</b>
<span>点击上方「刷题中心」做题，或从文档中提取题目</span>
```

> **同组件、同 CSS、仅 props 不同 → 结果一个空白一个正常。因果链完全闭合。**

#### ⑤ 影响范围与准确表述

| 项 | 数据 |
|---|---|
| 失效调用点 | **6 处** |
| 受影响"暂无数据"提示 | **16 处** |
| 影响程度 | **局部失效** —— 页面其余部分完全正常 |
| 佐证 | `/quiz-section` 整页 `mainTextLen=2206`；`visibleTextNodes=211` |

**准确表述**：**16 处"暂无数据"提示不可用，每一处都渲染成一个纯空白卡片。**

**错误表述**（必须避免）：~~"16 个页面崩溃"~~、~~"页面大面积白屏"~~。

#### ⑥ 取证陷阱（⚠️ 极其重要）

**这个缺陷必须用移动端宽度拍摄，桌面端拍不到。**

原因是：桌面端被 **P0-0（白屏）** 遮挡 —— `main` 被顶到 y=900（视口外），**桌面截图只能拍到侧边栏**，主内容区根本不在画面里。

> **结论：P0 必须逐个验证，验证时必须选对视口。**

#### ⑧ 修复方案

**改哪里**：`frontend/src/components/UI.jsx:64-73`。**改组件，而不是改 6 处调用方** —— 理由见下方。

```jsx
/* ---------- 空状态 ---------- */
/* 批次0-2 修复：
   ① 旧签名 ({icon,title,desc,action}) 不接收 text，导致 6 处 <Empty text="..."/> 全空白；
      这里把 text 作为 title 的别名（兼容），同时补 desc 缺省，避免二次踩坑。
   ② .es-ico 全项目未定义（真实类名是 global.css:1000 的 .empty-state-icon）；
   ③ 裸 <b>/<span> 未挂 .empty-state-title/-desc，字号/颜色/间距全失。
   注意：不要改 .empty（v2-design.css:558 另一套样式），只对齐 global.css:996-1003 已有的类。 */
export function Empty({ icon, title, text, desc, action }) {
  const heading = title ?? text
  return (
    <div className="empty-state">
      {icon && <div className="empty-state-icon">{icon}</div>}
      {heading && <div className="empty-state-title">{heading}</div>}
      {desc && <div className="empty-state-desc">{desc}</div>}
      {action && <div className="empty-state-action">{action}</div>}
    </div>
  )
}
```

> ### ⚠️ 为什么改组件而不是改 6 处调用方（必答）
>
> **理由 1：改调用方要动 6 个文件。**
> `Analysis.jsx:240` + `QuizSection.jsx:120,143,165,181,199`，跨 2 个页面。而且**以后任何人再写 `<Empty text=>` 都会重新踩坑**。改组件是 1 个文件、**1 处签名**。
>
> **理由 2：`.es-ico` 和裸标签这两个 bug 在组件内部，改调用方完全解决不了。**
> 必须改 `UI.jsx`。既然动了，把 `text` 一起兼容掉是**零边际成本**。
>
> **理由 3：向后兼容。**
> `title` 仍可用，现有 4 处正确调用（`Notebook:554`、`Pan:233`、`QuizBank:132`、`Tasks:334`）**不受影响**。
>
> **代价与建议**：这会让"接口有两个别名"成为长期事实。**建议同时在 6 处调用方把 `text=` 机械替换为 `title=`，改完后 `text` 别名仅作历史兼容保留。** 这比只改一边更干净。

### 4.4 P0-3 移动端择校模块 12 页进去出不来

#### ① 现象

375px 手机上，用户点进任何一个择校子页（院校库 / 院校对比 / 热力图 / 散点图 / 智能择校 / 分数分析…），然后**找不到任何出口**：

- 底部导航栏只有 6 个图标：**今日 / 错题 / 考点 / 刷题 / AI / 我的** —— **没有择校**
- 侧边栏在 ≤860px 时是 `display:none` —— **看不到**
- 页面内8/12 个子页一个可点的返回链接都没有

**用户想离开这个模块，只能按浏览器的后退键。** 如果他是从别的模块直接用 URL 进来的，那连后退都不知道该退到哪。

**整个 12 页的择校模块，在手机上是一座单向门。**

#### ② 复现

```
视口宽度：375 × 812
路由：/#/kaoyan/map（或任意 kaoyan 子页）
步骤：
  1. 375px 视口打开 /#/kaoyan/guide（择校中心，内容正常显示）
  2. 点击进入任一子页，如"区域热力图"
  3. 尝试找离开该模块的方式
预期：底部有择校入口，或页面内有 Tab/面包屑
实际：
  - 底部导航 6 项：今日 / 错题 / 考点 / 刷题 / AI / 我的（无择校）
  - 侧边栏 display:none，不可见
  - 页面内 0 个 kaoyan 互链
  → 只能靠浏览器后退键
```

#### ③ 根因机理（三重叠加）

**每一处单独看都合理，三处叠在一起就成了死胡同。**

**第一重：底部导航漏了择校**

```jsx
/* Layout.jsx:70-77 —— BOTTOM_NAV 只有 6 项 */
const BOTTOM_NAV = [

  { to: '/notebook',label: '错题', icon: FileText },
  { to: '/kbmap',     label: '考点', icon: Map      },
  { to: '/quiz',      label: '刷题', icon: Book     },
  { to: '/assistant', label: 'AI',   icon: Brain    },
  { to: '/settings',  label: '我的', icon: Settings },
]
```

设计时按"高频功能"选了 6 项。**择校是后加的模块，选这 6 项时它还不存在** —— 于是它既不在底部导航，也不在设计时被考虑进"高频"。

**第二重：兜底出口被关掉了**

```css

```

侧边栏原本注册了 10 个 kaoyan 入口（择校中心 / 院校库 / 院校对比 / 区域热力图 / 招生散点图 / 智能择校 / 考研规划 / 成长体系 / 择校 AI 问答 / 数据管理）。

**在桌面端它是完美的兜底出口。但在 ≤860px 时它被隐藏了** —— 而这恰好是移动优先改造时"该隐藏的东西"。

**移动端四条路全断，只剩浏览器后退。**

#### ④ 定级纠偏（为什么从 P3 上调到 P0）

### 4.5 P0-4 单词列表永远加载失败

#### ① 现象

用户打开单词页，看到"没有单词"。

**而实际上数据库里有 4569 个单词。**

用户不会怀疑是数据问题 —— 因为页面上没有任何错误提示。他会以为：是不是还没导入？要不要去别的地方设置？**但无论如何他都想不到，问题在于前端请求里一个写错的数字。**

#### ② 复现

```
视口宽度：任意（桌面端会被 P0-0 白屏遮蔽，需用 375px 观察控制台）
路由：/#/words
步骤：
  1. 直连后端验证
     curl "http://127.0.0.1:8000/api/words?page=1&page_size=2000"
预期：HTTP 200
实际：HTTP 422 Unprocessable Content

  2. 观察响应体
实际：
  {"code":"INVALID_PARAMETER","message":"请求参数校验失败",
   "detail":{"errors":[{"field":"query.page_size",
     "message":"Input should be less than or equal to 500",
     "type":"less_than_equal"}]}}
```

**这条 422 是 100% 可复现的，与前端运行时无关。**

#### ③ 根因机理（一个"契约"从未被定义）

**第一层：前端把"一次拉全量"当成了契约**

```jsx
/* Words.jsx:63、191、224 —— 三处硬编码 */
const backendWords = await wordsApi.list({ page: 1, page_size: 2000 });
```

**三处都是 2000。** 这是典型的复制粘贴产物 —— 写第一处的人可能想让"一次拿全"，随手写了个 2000，然后粘贴到另外两处。

**第二层：后端为保护数据库设了上限**

```python
# backend-main-fastapi/routers/words.py:142
def list_words(page: int = Query(1, ge=1),
               page_size: int = Query(50, ge=1, le=500)):
    ...
```

**`le=500` 是有意的** —— 这是一个带分页语义的列表接口，上限防止单次全表扫描。

**第三层：两边从未对齐过**

前端没有读过后端接口定义（无 OpenAPI 消费、无类型生成），后端也没有文档化这个限制（接口对接手册里没写）。**两个数字从一开始就不一致，只是恰好以前没人访问单词页，所以没暴露。**

**2000 > 500 → 必然 422。** 不是"偶尔失败"，是"一定失败"。

#### ④ 静默 catch 让契约缺陷伪装成了"数据为空"

这是本缺陷**最值得警惕的一点** —— 它本该是 P1（体验问题），但因为下面这行代码，它升级成了"用户被误导"：

```jsx
.catch(() => {})   // 吞掉错误，什么都不显示
```

**422 被 catch 掉，界面显示"没有单词"。**

用户看到的是一个**看起来正常但完全是错的**结果 —— 这比报错更糟。报错至少会让人去查，沉默的失败会让人相信"就是这样"。

**这也解释了为什么它被定为 P0 而不是 P1**：它不是"功能缺失"，是**"功能在说谎"**。

#### ⑤ 影响范围

| 项 | 数据 |
|---|---|
| 硬编码位置 | **3 处**（`Words.jsx:63`、`:191`、`:224`） |
| 后端上限 | `le=500`（`words.py:142`） |
| 实际单词数 | 4569 条 |
| 用户影响 | 单词页 **100% 无法使用** |
| 隐蔽性 | 高（静默 catch，用户看到的不是错误） |

#### ⑥ 证据

![单词页桌面首屏](images/05-words.png)

*图 4-16　单词页桌面首屏（第一轮取证）。**注意这是"白屏掩盖功能缺陷"的典型例子** —— 用户先看到的是 P0-0 的白屏，而不是 422。这个页面的真实问题是"永远加载失败"，但首屏表现只是"空白"*

![单词页桌面首屏（第二轮复测）](images/20-words.png)

*图 4-17　单词页桌面首屏（第二轮复测，14 张截图之一）。两轮取证都未真正渲染出单词内容。**真正的证据在网络层：2 次 422，响应体明确写着 `page_size` 必须 ≤ 500***

**网络层铁证（`runtime-report.json`）：**

```

响应体原文（直连 8000 验证）：
  {"code":"INVALID_PARAMETER","message":"请求参数校验失败",
   "detail":{"errors":[{"field":"query.page_size",
     "message":"Input should be less than or equal to 500",

```

#### ⑦ 修复方案

**改哪里**：`frontend/src/pages/Words.jsx:63`、`191`、`224`。**改前端，不改后端。**

```jsx
// 批次0-3：后端 words.py:142 限制 page_size<=500，硬编码 2000 必然 422。
// 单词词库是个人单机应用，千级词汇量足够；这里取后端允许的上限 500。
// 若真实词库可能超过 500 条，正确做法是分页拉取（见批次2 的 P1-6 补齐建议），
// 但当前 500 已覆盖绝大多数个人词库，且立即解除恒定 422。
const backendWords = await wordsApi.list({ page: 1, page_size: 500 });
```

> ### ⚠️ 该改前端还是后端？—— 改前端（必答）
>
> **理由 1：`le=500` 是后端故意的保护。**
> `words.py:142` 是带分页语义的列表接口，放开上限等于允许单次全表扫描。**改后端是把"有界查询"改成"无界查询"，是降低安全性换前端方便，方向错误。**
>
> **理由 2：3 处硬编码 2000 说明是复制粘贴的产物**，不是有意的契约设计。真正的契约应该是后端定义的 `50/500`。
>
> **理由 3：成本对比。**
> 改前端 3 行 / 立即生效；改后端 1 行，但要评估全表扫描风险 + 可能影响其他调用方（`sync.js` 的 hydrate 也拉 words）。
>
> **⚠️ 潜在数据丢失（必须诚实交代）：**
> 若用户词库真实超过 500 条，改完后 `words` 列表会**只显示前 500 条**。
> 因为 `:191`/`:224` 有第二/第三处兜底加载，实际会覆盖到部分场景，**但必须在 UI 上体现"共 N 条，仅显示前 500"**，否则用户会以为数据丢了。
> **这一点必须与 P1-6（空状态补齐）一并处理。**

## 5. 前端工程问题

> **本章定位**：本章问题**不影响任何功能的可用性**（除了 5.5 的孤儿路由），因此全部为 P2/P3 结构债。
> **它们被隔离到批次 3，不能与修bug 的批次混做。** 详见 §7.5。

### 5.1 双设计体系：令牌冲突与"加载顺序决定外观"

#### 现象与定级

项目里**两套设计体系同时生效且互相覆盖**。这不是"样式没写好"，而是**实际生效的视觉方案由文件加载顺序决定，而非设计意图**。

**定级：P2（结构债），风险等级：高。** 因为它让界面"难看且不一致"，但**不会让任何功能不可用**。

#### 根因机理

```javascript
// main.jsx:5-6 —— 连续 import 两份 CSS
import './styles/global.css'      // 90 KB / 2650 行
import './styles/v2-design.css'   // 35 KB
```

**CSS 的层叠规则：同特异性的规则，后加载的胜出。**

两份 CSS 都用了 `:root` 定义同名变量，`v2-design.css` 在后面 → **它的值覆盖 `global.css` 的值**。

于是出现了一个**极其反直觉的后果**：

> **开发者打开 `global.css` 看到 `--accent: #2f4b6e`（墨蓝），改了半天，但页面上一点变化都没有** —— 因为实际生效的是 `v2-design.css` 的 `#1e6fd9`（亮蓝）。

#### 令牌冲突硬数据

| 变量 | `global.css` 写的值 | **实际生效（v2）** | 视觉差异 |
|---|---|---|---|
| `--accent` | `#2f4b6e`（墨蓝） | **`#1e6fd9`（亮蓝）** | 明显，色相与饱和度都变了 |
| `--bg` | `#f4f1e9`（暖纸） | **`#f4f6fb`（冷蓝）** | 明显，色温完全相反 |
| `--r-md` | `14px` | **`16px`** | 细微但累积 |
| `--red` | `#b0442e`（暗红） | **`#e0524a`（亮红）** | 明显 |

**冲突总量：32 个变量、116 个类在 `global.css` 内被重复定义 2–15 次。**

#### 最刺眼的一处：代码与设计意图已完全脱节

```css
/* global.css:1-5 —— 头部注释 */
... 学术档案美学 · 暖纸底色 × 墨蓝主色...
```

**而实际渲染的是 v2 的亮蓝冷调。**

**注释里写的设计方案，和用户看到的界面，是两回事。** 这是"设计意图"与"实现"脱节的直接证据 —— 也是为什么本报告坚持**这个问题必须先做产品决策**（见 §7.5）：连"这个产品应该长什么样"都没有共识的情况下，任何重构都是在猜。

> ### ⚠️ 为什么这类问题最消耗团队精力
>
> 因为它**让"改样式"这件事变成不可预测的**。
>
> 新人想调整主色，打开 `global.css`（因为文件名最像"主样式"），改完发现没效果；去搜发现还有 `v2-design.css`；改完发现影响面比想象大，因为116 个类被重复定义过……**每一次样式修改都要先做考古。**
>
> **这类债的成本不在于"现在不好看"，而在于"以后每次改都要付额外的时间"。**

### 5.5 孤儿路由与信息架构缺口

#### 三个孤儿路由

实测 `NAV_GROUPS` 共 **23 个去重项**，以下三个路由的命中数**均为 0**：

| 孤儿路由 | 路由注册处 | 为什么重要 | 批次 |
|---|---|---|---|
| **`/settings`** | `App.jsx:73` | **全站配置中枢**：AI 密钥 / 后端地址 / 主题全在这里 | 批次 0 |
| `/quiz-bank` | `App.jsx:64` | 三个刷题兄弟（`/quiz`、`/quiz-section`、`/analysis`）都有导航入口，唯独它被藏起来 | 批次 0 |
| `/kaoyan/analysis` | `App.jsx:81` | 择校 12 页里只有它不在导航；guide 页已把它列为"分析工具"区第 3 位 | 批次 0 |

#### 最反直觉的一个：手机能进设置页，桌面进不去

```
移动端 BOTTOM_NAV（Layout.jsx:76）：包含 /settings  ✓
桌面 NAV_GROUPS（Layout.jsx:14-65）：  不含 /settings  ✗
```

**可达性与响应式的方向也是相反的** —— 和"桌面白屏、移动正常"形成了一个完整的镜像：**桌面在所有维度都比移动端差。**

**这给用户造成的实际困扰**：他在手机上学会了怎么改AI 密钥、换主题，然后坐到电脑前想改同样的设置，**找不到入口**。

#### 成因分析

**三个孤儿路由有同一个成因：导航配置没有随路由表同步更新。**

```
App.jsx 新增路由 → 开发者在页面内加了链接 → 忘了同步 NAV_GROUPS
```

这是一类典型的**配置重复**问题 —— 路由表在 `App.jsx`，导航表在 `Layout.jsx`，**两处独立维护，没有一致性校验**。

**根本解法不是手动补齐，而是加一个测试**（见 §6.4第二层的`nav.coverage.test.js` 方案）：把 `NAV_GROUPS` + `BOTTOM_NAV` 导出后与路由表 diff，缺项即测试失败。**这样一次性拦住所有未来的导航漏配。**

### 5.7 正面范本：`.src-badge` 同批交付模式

> **本节是本章唯一在"表扬"的内容 —— 但它比任何批评都更有价值，因为它指出了"应该怎么做"。**

#### 项目里唯一的规范写法

14:06–14:07，一个并发任务新增了择校数据来源角标，它的方式是：

```
同批交付：global.css 加 .src-badge        （样式）
    ↓ 同批新建
         components/SourceBadge.jsx 第 40 行 className="src-badge"   （组件）
    ↓ 同批修改
         pages/KaoyanSchoolDetail.jsx import 并使用                 （消费方）
```

**CSS 类与消费它的组件同批落地 → 不会成为死代码。**

这是本项目里**唯一一处"类与组件同批交付"的写法**，也是 §5.2 那390 个死 CSS 的**正确反面**。

#### 第二个案例：`KaoyanCompare.jsx` 的口径纠偏

`KaoyanCompare.jsx`（+31/−18）的改动实质是**数据口径纠偏**，代码注释写明：

> 后端 `/analysis/compare` 只返回 `total_line` / `retest_line` / `enroll_count` / `admit_count` / `admit_avg_score` 五个字段，
> 其中 **`retest_line` 与 `total_line` 同值**、**`admit_count` 为伪造列**，
> 故此处**只对比 3 个可信指标**。

**这是一次"把不真实的指标从界面上拿掉"的正确动作** —— 它没有掩盖数据问题，而是**主动缩小了承诺范围**。

同时它引入了 `SourceBadge` 与 `useThemeTokens`，同样是"CSS + 组件 + 消费方同批"。

#### 从两个案例提炼出的可复制规则

**批次 3 收敛择校 12 页视觉时，必须照抄这个范式：**

| 规则 | 说明 |
|---|---|
| **规则 1** | 新样式必须与其消费组件**同批提交**，不能"先撒 CSS 再补 JSX" |
| **规则 2** | 颜色一律走主题变量（`var(--*)`），**不硬编码** |
| **规则 3** | 确需新增 class 时，同步在同批 JSX 中引用 |

> ### ⚠️ 这条规则改变了批次 3 的原定做法
>
> 最初建议是"抽 `.page-wrap` / `.ky-card` 等新 class"，但**当前 46% 的死代码率正是"先撒 CSS 再补 JSX"堆出来的** —— 如果批次 3 沿用那个思路，**做完之后死 CSS 会更多而不是更少**。
>
> **修订后的做法：把"新增 class"与"消费该 class 的组件改动"绑成同一个原子提交。**

### 6.2 为什么 61 个测试也拦不住 P0-0

**已实测证实：61 个用例全绿，而 P0-0 此刻依然存在**（`global.css` 仍只有 541 行一处 `.mobile-top` 定义）。

这不是假设，**这是刚刚发生的实证**：测试规模从 3 扩到 61（×20），对 P0-0 的拦截能力**零提升**。

#### 三层结构性盲区

**盲区 1：jsdom 没有布局引擎**

```jsx
// pages.smoke.test.jsx 的断言
expect(result.container.firstChild).toBeTruthy()
```

这只验证 **DOM 节点存在**。而 P0-0 的本质是：

| 项 | 值 |
|---|---|
| `main` 节点是否存在 | ✅ **存在** |
| `main` 里有几个字符 | **582** |
| `main` 在视口的哪个位置 | **y=900（视口外）** |

**jsdom 不执行 CSS grid 布局，压根不知道元素被挤到了屏幕下方。** 任何基于 jsdom 的测试都无法捕获这类缺陷 —— 这不是"写得不够仔细"，是**工具的能力天花板**。

**盲区 2：测试只渲染页面组件，不渲染 `<Layout>`**

```jsx
// pages.smoke.test.jsx:113-116
<MemoryRouter><Comp /></MemoryRouter>
```

**没有 `<Layout>`、没有 `<App>`。**

而 P0-0 的根因在 `Layout.jsx:183-234` 的 `.app-shell` 子元素顺序 + `global.css:127-131` 的 grid 定义。

> **测试根本没渲染出出问题的那一层，等于测了一个不存在的组件树。**
>
> 这就像测试一个函数的行为，却没调用它依赖的那个模块 —— 测的和坏的压根不是同一个东西。

**盲区 3：只断言"存在"，不断言"可见"**

```jsx
// smoke.test.jsx:76,81,86
expect(...).toBeInTheDocument()
```

| 断言 | 语义 | P0-0 的实际情况 |
|---|---|---|
| `toBeInTheDocument()` | "节点在 DOM 树里" | ✅ **满足** |
| （用户期望的）"在视口里" | "节点在可见区域" | ❌ **不满足** |

**断言强度与缺陷性质错配。** `toBeInTheDocument()` 的语义是"树里有"，而 P0-0 的语义是"视野里"。

#### 一个值得肯定的地方

`pages.smoke.test.jsx:132-140` 的 `withCrashCapture`：

```jsx
// 显式监听 window.onerror，把"渲染崩溃"变成显式断言
// 注释里还写明了"页面崩了测试也会通过（假绿）"
```

**这是写得很好的一段 —— 作者已经识别了假绿风险。**

但它**只覆盖了 JS 崩溃，没覆盖 CSS 布局失效**。

**这说明问题不是"作者不懂测试"，而是"jsdom 这个工具的天花板"。** 这也是为什么 §6.4 第一层（Playwright 几何断言）**不能省** —— 再多 jsdom 用例也补不上这个洞。

### 6.3 两条否证与"传输层加固 ≠ 视觉层修复"

grep -l "Empty"     src/test/*  →  0 命中（没有任何用例触及 P0-1）
grep -c "mobile-top" pages.smoke.test.jsx  →  0（没有任何用例触及 P0-0）

**61 个用例中，无一条涉及**：
- kaoyan 导航（P0-3 / D13）
- `page_size` 上限（P0-4）
- `/agent/auth`（P0-2）
- `NAV_GROUPS` 完整性（P1-1/P1-2）

#### 新增用例的真实分布

| 文件 | 用例 | `describe` 主题 | 层级 |
|---|---:|---|---|
| `client.contract.test.js` | 32 | `request URL 与参数拼装` / `request method 与 body` / `响应解析` | **API 传输层** |

#### 定性结论

> **这批改动不是"跑偏"，是根本没进入 UI 层。**
>

**新造58 个用例里没有一条几何或可见性断言 —— 测试架构对"渲染位置"和"视觉呈现"完全无感知。** 补再多同类型用例也抓不到 P0-0 与 P0-1。

> ###⚠️ 这是比"测试通过"更强的结论
>
> 通常"测试通过"是一个正面信号。
>
> 但这里它是一个**警告信号**：**它证明了当前的测试架构无法捕获它本该捕获的那类缺陷。**
>
> **在测试数量从 3 涨到 61 的同时，缺陷数量一点没降** —— 这说明覆盖率数字的提升与被测对象的改善**完全脱钩**。

### 6.4 补什么测试：三层补齐方案

**必须分三层，缺一不可。**

#### 第一层：视觉回归（唯一能拦住 P0-0 的手段）

用 Playwright 截图对比（现成的 `evidence/verify.mjs` 已是骨架，可直接改造为回归基线）：

- **至少 3 个视口**：375×812 / 768×1024 / **1440×900**（桌面是本次漏测的致命点）
- **至少 3 个代表路由**：`/`、`/planner`、`/kaoyan/map`

**核心断言不是"像素完全相同"**（会因字体/数据波动误报），**而是几何断言**：

```js
// tests/e2e/layout.spec.js
const main = await page.locator('main.main-area').boundingBox()
expect(main.y).toBeLessThan(viewportHeight)   // ← 这条断言会直接抓住 P0-0
expect(main.height).toBeGreaterThan(100)
```

**这条断言的语义就是"主内容区首屏可见" —— 恰好是用户诉求本身。**

把它固化成断言，白屏这类缺陷就再也跑不掉了。

#### 第二层：契约与渲染断言（拦 P0-1 / P0-2 / P0-4）

| 要拦的缺陷 | 补什么断言 | 建议落点 |
|---|---|---|
| **P0-1** 空状态空白 | `<Empty text="x"/>` 渲染后 `screen.getByText('x')` **可见**（用 `toBeVisible()` 而非 `toBeInTheDocument()`）；`document.querySelector('.es-ico')` 应为 `null`（拼写错误防回归） | 新建 `src/test/empty.test.jsx` |
| **P0-2** Agent 死接口 | **契约测试**：遍历所有前端 api 封装调用的路径，与一份后端路由清单快照比对，404 / 不存在即失败。`client.contract.test.js:266-284` 已有 10 个 `it.each` 路径用例的**正确范式** —— 把 `/agent/*`、`/sessions*`、`/api/chat` 补进去会**立刻变红** | 扩展 `client.contract.test.js` |
| **P0-4** 参数越界 | 同上机制：`wordsApi.list` 的 `page_size` 必须 ≤ 500（从后端常量读）。**这是"前后端契约"该有的测试形态** | 扩展 `client.contract.test.js` |
| **P0-3** 移动端死胡同 | Playwright 375px 下遍历 12 个 kaoyan 路由，断言"页面上存在至少一个指向非自身路由的可点击元素" | 视觉回归层 |
| **P1-1/P1-2** 孤儿路由 | 断言**每个 `App.jsx` 注册的路由**都能从"导航配置数组"中找到对应项。做法：把 `NAV_GROUPS` + `BOTTOM_NAV` 导出后与路由表 diff，缺项即失败 —— **这类断言能一次性拦住所有未来的导航漏配** | 新建 `src/test/nav.coverage.test.js` |
| **P1-3** 死变量 | 断言组件读取的 store 键都真实存在：`Object.keys(useStore.getState())` 必须包含所有被读取的键 | 新建 `src/test/store-contract.test.js` |

#### 第三层：CI 闸门

- `npm run test` 增加**最少用例数**断言（关闭 `--passWithNoTests` + 断言总数 ≥ N），**防止"测试文件被误删/ 未执行"导致假绿**
- 把 Playwright 视觉回归加入 CI，**每次 PR 必须跑桌面视口**
- **契约测试的前后端路由清单快照必须入库** —— 否则快照本身会过期

### 6.5 反模式清单：不要用覆盖率数字当质量指标

#### 五个反模式（本项目全部踩过）

| # | 反模式 | 本项目的表现 | 正确做法 |
|---|---|---|---|
| 1 | **把用例总数当覆盖率** | 3 → 61 条"大涨"，但P0 一个没抓到 | 看**缺陷拦截率**：修好的 bug 有多少是被测试挡住的 |
| 2 | **把"能渲染出文本"当"渲染正确"** | `toBeInTheDocument()` 放过白屏 | 对关键路径加**可见性 / 几何**断言 |
| 3 | **测试组件而不是组件树** | 只渲染页面，不渲染 `<Layout>` | 关键路径测**完整组件树** |
| 4 | **同类型用例无限复制** | 58 个新增用例全是传输层 | 先问"这个测试能拦住哪类缺陷"，答不上来就别加 |
| 5 | **让测试跑在被修复之前的代码上** | 61 条全绿时P0-0 仍在 | 修复后**立即重跑**，把"修复后测试仍全绿"作为验收条件 |

#### 一条应该写进团队规范的话

> **测试的价值不是"有多少"，而是"能拦住什么"。**
>
> 一个 3 条用例但包含几何断言的测试套件，比 61 条只断言"节点存在"的测试套件**更能保护这个项目**。

### 7.6 🔴 硬前置依赖：D1 未修前桌面 UI 改动无法验收

### 9.5 术语表

| 术语 | 含义 |
|---|---|
| **白屏** | 本报告中特指 P0-0：桌面端主内容区被推到视口外，不是"页面崩溃" |
| **静默失效** | 不报错、不进控制台、只在界面上表现为空白或"没有数据"的失效 |
| **孤儿路由** | 已在 `App.jsx` 注册但不在任何导航配置里的路由 |
| **死 CSS** | 在 CSS 文件里定义但从未被任何 JSX 引用的类 |
| **内联样式** | 直接写在 JSX 的 `style={{}}` 属性里的样式，无法被主题变量统一控制 |
| **双设计体系** | `global.css` 与 `v2-design.css` 同时生效，实际生效值由加载顺序决定 |
| **MD5 相同的截图** | 两张不同页面的截图字节完全一致 → 渲染结果完全一致（常意味着都是空白） |
| **几何断言** | 断言元素的坐标/尺寸（`boundingBox`），而非只断言存在性 |
| **有界查询** | 带 `le=` 上限的列表接口，防止单次全表扫描 |
| **`strangler` 模式** | 绞杀者模式 —— 先加新路径、再逐个切流、最后删旧路，避免一次性重构 |
| **口径** | 统计数字时界定的范围（如"是否含 CSS 文件内的颜色"）—— 引用计数型数据必须带口径 |
| **可引用性** | 某个行号/数字在最新代码状态下是否仍然准确 |

## 结语：三句话总结

1. **最严重的问题只有一个**：`global.css` 缺 `.mobile-top` 的基准 `display:none`，导致桌面端（用户真正使用的场景）整个网站白屏。**1 行 CSS 修复，1 小时内可完成。**

2. **第二严重的是"静默失效"文化**：空状态组件签名与调用方不匹配、store 键名读写不一致、13 处 `catch(() => {})` 吞错、AI 助手对着 9 个不存在的后端端点空转。**这些都不会报错，只会静默地让用户看到空白** —— 这才是"界面有极大问题"的真实成因，不是视觉设计。

3. **视觉不一致（双设计体系）是重构，不是 bug**。它让界面难看，但不影响任何功能。**必须在功能问题修完、且用户拍板设计方向之后，才单独启动。**
