## 1. 为什么要做 AI 完善

### 1.1 四个已实测的现状事实

> ## 🔴 重结论一：AI 对话链路当前是完全不可用的，而界面看起来是正常的
>
> **三重失效叠加 —— 而用户看到的界面完全正常。**
>
> | # | 失效 | 实测证据 |
> |---|---|---|
> | **1** | **本地引擎 100% 抛异常** | `ai_router.py:368` 引用未定义变量 `route`，**必然 NameError**。实测 `force_local:true` 仍返回 `engine_used:"api"`、`fallback_used:true` |
> | **2** | **云端全部无密钥** | `ai_providers` 表 3 个云端服务商 `api_key` **均为 NULL**（实测 SQL）。默认服务商"豆包（默认）"`is_default=1` 但无 key |
> | **3** | **质量门控游离在链路外** | `retrieval_gate.py` 双阈值门控（0.50/0.60）实现完整，但**只被 `routers/gate.py` 调用**，而前端从不调 `api/gate`。检索不到就是硬答 |
>
> **三者叠加的后果**：
>
> ```
> 用户提问
>   ↓
> 走 /api/ai/chat（不是 /chat/router，因为前端从不调后者）
>   ↓
> _route_query() 关键词路由 → 判断该走 local
>   ↓
> 调 local → 抛异常 → except 吞掉 → 回退 online
>   ↓
> online：13 个服务商逐个重试 → 前 3 个是云端且无 key → 全部失败
>   ↓
> 继续回退 → 终于碰到第 4 个（ollama 本地）→ 勉强成功
>   ↓
> 每次请求浪费 9 次失败往返
> ```
>
> **而这一切在界面上看不出来** —— 用户只会觉得"AI 有点慢"或"答得不太好"，不会知道它刚刚失败了 9 次。
>
> **这条比"AI 不够聪明"重要得多** —— 一个不够聪明的 AI 用户会放弃；一个看似可用实则不可用的 AI，**用户会把错误的择校建议当真**。

> ## 🔴 重结论二：择校推荐**根本不是 AI** —— 这个信息不对称比技术缺陷更危险
>
> **用户以为在看"AI 推荐"，实际看到的是一段固定公式。**
>
> **实测事实**：
>
> | 项 | 实测结果 |
> |---|---|
> | "智能择校"的实际实现 | **`routers/kaoyan.py:214` 的 131 行硬编码 SQL 权重** |
> | 是否走 AI 层 | ❌ **完全不走** |
> | 是否有质量门控 | ❌ **完全没有** |
> | 它用的数据 | 97.29% 未核验 + 44% 院校覆盖（见 §6.1） |
>
> **这意味着两件事**：
>
> **第一，即使 AI 层全部修好**（批次 A/B/C 全部完成），**用户在"智能择校"页看到的也不是 AI 的判断** —— 而是一段自始至终没变的 SQL 权重。
>
> **第二，它用的数据基础很软** —— 493 所院校里只有 217 所有分数线，唯一可信的官网来源只覆盖 5 所。
>
> > **为什么这个信息不对称比技术缺陷更危险**：
> >
> > 技术缺陷（页面报错、功能不可用）会**提醒用户"这里有问题"**，用户会绕开或反馈。
> >
> > **信息不对称不会提醒任何东西** —— 界面排版专业、结果看起来像模像样，用户会**把它当作 AI 的判断并据此决策**。
> >
> > **一个诚实的固定公式，比一个假装是 AI 的固定公式更安全。**
>
> **建议处置（三选一，推荐 C）**：
>
> | 选项 | 内容 | 代价 |
> |---|---|---|
> | A | 改名为"院校匹配" | 诚实，但失去 AI 卖点 |
> | B | 让 AI 真正参与 | 成本高，**且数据未达标前不该做**（见 §5.6） |
> | **C（推荐）** | **保留公式，但在结果旁标注"基于 N 条数据，其中 M 条未核验，覆盖 X/Y 所院校"** | **最低成本，且把信息不对称消掉** |
>
> 详细讨论见 §5.6（L4 会择校）与 §2.10（四路并存的硬编码旁路）。
>
> **这条结论比"AI 不够聪明"重要得多。** 一个不够聪明的 AI 用户会放弃；一个看似可用实则不可用的 AI，用户会把错误的择校建议当真。

### 1.2 事实一：AI 对话"看似可用，实则失效"

#### 现象

界面上的 AI 助手有完整的对话 UI、流式输出、4 个引擎切换选项。**看起来是完整的。**

但实际链路是断裂的。

#### 根因 1：`ai_router.py:368` 的 NameError（本地引擎 100% 失效）

```python
# services/ai_router.py:356 —— 定义
route_result = await self.route(question, context, force_engine)

# services/ai_router.py:368 —— 使用（★ BUG）
result = await self._chat_local(question, context, subject=route.get("subject"))
#                                                   ^^^^^^ 未定义！
```

**变量名是 `route_result`，代码里用的是 `route`。**

`route` 在整个文件里**从未被赋值** → 调用 `route.get("subject")` 必然抛 `NameError`。

**为什么是静默的**：

```python
# 异常被 except Exception 吞掉
except Exception:
    last_error = ...
    # → 静默降级到 fallback 链
```

`NameError` 是 Python 内置异常，会被 `except Exception` 捕获。**代码不会崩，会静默降级。**

#### 实测铁证（P0-1 的核心证据）

```
POST /api/ai/chat/router
  请求：{ "question": "什么是卡诺图", "force_local": true }
  响应：{
    "engine_used": "api",           ← 请求强制 local，实际返回 api
    "fallback_used": true,            ← 确认走了降级
    "reason": "强制使用local引擎",     ← 理由说用了 local
    "classification": { "preferred_engine": "local" }   ← 分类也说该用 local
  }
```

**三个字段互相矛盾**：`reason` 和 `classification` 都说是 local，实际 `engine_used` 是 `api`。

**这不是配置问题、不是模型问题、不是网络问题 —— 是一行变量名写错的确定性 bug。**

> **这条的严重性**：文档 `模型选型与分科路由.md:193-194` 宣称"已实现本地优先 + 云端兜底"。**实际本地优先 0% 生效。**
>
> 而前端 **0 消费该端点**（grep `chat/router` 前端 0 命中）→ **故障完全静默，无人发现**。

#### 根因 2：云端服务商全部无 API Key

**实测 `ai_providers` 表：**

| id | name | provider_type | is_default | is_enabled | `LENGTH(api_key)` |
|---:|---|---|:-:|:-:|---:|
| 1 | 豆包（默认） | doubao | **1** | 1 | **NULL** |
| 2 | DeepSeek | deepseek | 0 | 1 | **NULL** |
| 3 | 通义千问 | qwen | 0 | 0 | **NULL** |
| 4–12 | 本地 ollama ×9 | ollama | 0 | 1 | 6（占位） |
| 13 | 考研专有答疑 kaoyan-qa | local-retrieval | 0 | 1 | 5（占位） |

**三个云端服务商的 `api_key` 全为 NULL。**

#### 后果：每次请求浪费 9 次失败往返

`ai_service.py:427-510` 的降级链是"逐个重试所有服务商"：

```
第 1 次：豆包（默认，无 key）        → 401 失败
第 2 次：DeepSeek（无 key）          → 401 失败
第 3 次：通义千问（无 key，已禁用）    → 跳过
...
第 4 次：本地 ollama               → 成功
```

**每一次成功的对话，前面都有 3 次必然失败的云端调用。**

在云端有 key 的情况下这是合理的降级设计（云端挂了走本地）。**但在"云端全部无 key"的情况下，这 3 次失败是 100% 浪费。**

#### 根因 3：检索质量门控游离在链路之外

```python
# services/retrieval_gate.py:28-33 —— 门控实现完整
QUALITY_GATE = {
    "accept_threshold": 0.50,
    "abstain_threshold": 0.60,
    ...
    "mode": "observe",     # 灰度模式
}
```

**grep 验证：`gate_and_retrieve` 全后端仅 `routers/gate.py:33` 一处调用。**

而前端 `grep "api/gate"` → **0 命中**。

**后果**：
- 用户走 `/api/ai/chat`（答疑主链路）→ **完全不经过门控**
- 检索不到就是**硬答**，**没有 abstain / 拒答机制**
- **这是 AI 编造答案的主要源头**

> 文档 `本地知识库建立与自愈.md` 描述的门控能力，**在实际答疑中完全没生效**。

### 1.5 不做的代价：择校域的 AI 错误是不可逆的

#### 择校是本平台的核心差异化功能

| 模块 | 规模 |
|---|---|
| 择校页面 | **12 个**（全站最重的模块） |
| 院校数据 | 493 所 / 832 个专业 |
| 涉及功能 | 院校库、对比、热力图、散点图、智能择校、分数分析 |

#### 为什么这个域的 AI 错误代价特别高

| 域 | AI 出错的代价 |
|---|---|
| 天气查询 | 用户多看一天预报|
| 翻译 | 用户自己会发现 |
| 写邮件| 用户会检查 |
| **择校建议** | **用户可能因此报了一所不该报的院校 —— 损失一年时间与金钱** |

**这不是"功能缺失"，是"功能危害"。**

一个不通的 AI 用户会放弃；**一个编造的 AI 用户会做出错误决策** —— 且因为它答得流畅自信，用户不会怀疑。

### 1.6 本报告的目标与非目标

#### 目标

**"可信的择校顾问"** —— 不是"更聪明的聊天机器人"。

三个可验证的目标：
1. **能用** —— AI 对话链路真正打通（不是静默降级）
2. **有据** —— 事实性回答带可溯源依据，无依据时明说
3. **可信** —— 引用不可信数据时必须标注，且趋势类结论在数据达标前不输出

#### 非目标（明确不做）

| 不做 | 理由 |
|---|---|
| 引入多智能体框架 | 个人/小团队项目，维护成本远超收益 |
| 追求通用能力 | 垂直场景的深度比通用能力更有价值 |
| 重新训练基础模型 | 6.5GB 的 LoRA 资产 + 现有 RAG 链路已足够，**先把链路打通再说** |
| 让 AI 替代用户做择校决策 | **产品定位应是"帮用户看得更清楚"，不是"替用户决定"** |

## 2. 现状诊断框架：AI 链路七层

### 2.1 为什么用"链路"而非"模块"来诊断

AI 能力"不好用"的原因，几乎从不是单点缺陷，而是**链路某层断了、上下层却以为它是通的**。

按层诊断的价值是：**能精确定位断点在哪一层**，从而知道该改哪一层、其余层要不要动。

| 传统"模块"视角的问题 | "链路"视角的改进 |
|---|---|
| 按功能分：`助手模块`、`择校模块` | 按依赖分：入口 → 调用 → 路由 → 服务 → 模型 → 检索 → 数据 |
| 一个功能可能横跨 5 层，改哪层说不清 | **断点定位到层，改动范围明确** |
| 跨层的问题（如"检索层有门控但服务层没接"）容易被漏掉 | **跨层断点正是链路视角的强项** |

**本报告的七层框架，每层标注四种状态之一：**

| 状态 | 含义 |
|---|---|
| ✅ **可用** | 已实测验证可用 |
| ⚠️ **部分可用** | 能用但有缺陷，或只在部分入口可用 |
| ❌ **不可用** | 有实现但实际不可用 |
| ☠️ **缺失/死代码** | 完全不存在，或 0 调用方 |

## 4. 完善方案分批次

### 4.1 批次划分原则与依赖图

#### 划分原则：按"可信度提升"排序，不按功能数量

| 批次 | 目标 | 一句话 |
|---|---|---|
| **A** | **能用** | 让 AI 真的能跑通，不再静默降级 |
| **B** | **可信** | 让 AI 答得有依据、敢于拒答 |
| **C** | **可扩展** | 把 4 路收成 1 路，为后续加能力铺路 |
| **D** | **会规划** | Agent + 工具调用 |

> **为什么 B 在 C 之前**（这是本方案最重要的一条排序判断）：
>
> **网关收口会让代码变好，但如果数据仍 97.29% 不可信，收口只是把不可信的答案更稳定地送达用户。**
>
> 先修可信度，再修架构 —— 否则会得到一个"架构很干净但仍在骗人"的系统。

#### 依赖图

```
        ┌─────────────────────────────────────────┐
        │  前置：择校推荐页下线                  │
        │ （否则等于要保留第 5 套硬编码逻辑）    │
        └──────────────────┬──────────────────────┘
                           ↓
  ┌────────┐      ┌────────┐      ┌────────┐      ┌────────┐
  │ 批次 A  │ ───→ │ 批次 B  │ ───→ │ 批次 C  │ ───→ │ 批次 D  │
  │ 让AI能用│      │ 让AI可信│      │ 让AI可扩展│ │ 让AI会规划│
  └────────┘      └────────┘      └────────┘      └────────┘
   P0-1 一行        门控接入        网关收口        Agent 能力
   P0-2 key过滤     硬编码动态化    删死代码        工具调用
   零成本 7 项      数据可信度标注  双路由统一      多轮会话

  跨批次依赖：
  · 批次 C 的前置是「择校推荐页下线」（否则保留第 5 套逻辑）
  · 批次 B 的「数据可信度角标」依赖批次 A 的字段语义纠偏
  · 批次 D 必须挂在统一网关上，否则又变成第 5 路
```

| **瓶颈** | `答疑模型训练指南.md:77` 指出：**"有确定答案的真题只有 293 道"** |
| **结构性问题** | 数学/英语/政治样本极少（训练集**偏科，数电+模电占 95%**） |
| **前置** | **必须先补真题答案** —— 没有答案就无法监督训练 |

#### D-5 建自动化质量评测（见 §7）

目前只有 2 份 eval 产物，且`lora_finetune/eval_result.json` **只测了 3 条**（`limit: 3`）且 `compare: false`（**未与基座对照**）。

**建议纳入 CI，每次改动跑回归。** 详见 §7。

### 4.6 批次总览表

| 批次 | 目标 | 改动量 | 依赖 | 风险 | 可感知变化 |
|---|---|---:|---|:---:|---|
| **A** | **让 AI 能用** | **~30 行 + 2 条数据 + 4 处文档** | 无 | **低** | AI 响应变快；本地引擎真正生效；不再浪费云端重试 |
| **B** | **让 AI 可信** | ~140 行 | 批次 A | **低**（observe 模式零风险） | AI 敢说"没找到依据"；引用未核验数据时明确标注 |
| **C** | **让 AI 可扩展** | **13–15 人时** | 择校推荐页下线 | **中** | 同一问题在不同入口答案一致；改一处即可全局切换模型 |
| **D** | **让 AI 会规划** | 视范围 | **批次 B + C 全部完成** | **中–高** | 多轮会话不丢上下文；工具调用有降级 |

#### 成本与收益的总体判断

```
投入（按批次递增）
A ████                        ~30 行，零风险，收益最大
B ████████                    ~140 行，低风险，核心价值
C ██████████████              13-15 人时，中风险
D ████████████████████        视范围，中高风险

收益（按批次）
A ●●●●●●  "突然变快了"        ← 一行代码，用户直接感知
B ●●●●●●●●●●  "敢信了"        ← 本报告的核心价值
C ●●●●      "好维护了"        ← 长期收益，不影响用户
D ●●●●●●    "能规划了"        ← 上限最高，但依赖前面全部达标
```

> **推荐执行顺序：A → B → C → D，其中 A 和 B 应尽快做完。**
>
> **理由：A + B 合计约 170 行改动，能把"看似可用实则失效"变成"真的可信"。这是性价比最高的投入。**
>
> **C 和 D 可以等A/B 的效果验证后再决定是否启动** —— 如果 A+B 做完后用户已经满意，D 的边际收益可能没那么高。

## 5. 能力建设路线

### 5.1 阶梯总览

#### 设计逻辑：每级只解决一个问题，且上一级不达标不允许进下一级

```
L4会择校    ← 结构化择校推理，每条带来源与置信度
            ┌───────────────────────────────┐
L3 会用工具  ← Agent + 多轮会话              │  前置：L2 达标
            ┌───────────────────────────┐   │  否则错误会被工具放大
L2 会规划    ← 任务分解与计划生成          │   │
            ┌───────────────────────┐   │   │
L1  有据    ← RAG 引用可溯源 +拒答 │   │   │  ← 本报告的核心
            ┌───────────────────┐   │   │   │
L0  可用    ← 基础对话能通│   │   │   │
            └───────────────────┘   │   │   │
             ↑ 当前实际卡在这里        │   │   │
             （且是"看似可用"）        │   │   │
```

> ### 为什么必须逐级递进
>
> **L1 没达标就做 L3（Agent），等于让一个会瞎编的模型去调工具 —— 错误会被工具调用放大而不是收敛。**
>
> 具体例子：如果门控没接入（AI-P0-3），AI 会编造分数线；Agent 拿着这个编造的分数线去调用"查询某院校录取情况"的工具 → **返回了一个基于编造前提的结果**，而用户看到的是一个"经过工具验证的"结论。
>
> **工具调用会让幻觉看起来更可信，而不是更不可信。这是最危险的组合。**

### 5.2 L0 可用：基础对话能通

| 项 | 内容 |
|---|---|
| **解决什么** | AI 对话真的能跑通，不再静默降级 |
| **当前状态** | ❌ **未达标** —— AI-P0-1（NameError）+ AI-P0-2（云端无key） |
| **达标标志** | ① `/api/ai/chat` 正常响应；② **本地引擎真正生效**（`engine_used:"local"`）；③ 错误有明确提示（不是静默重试） |
| **对应批次** | **批次 A**（~30 行） |
| **关键指标** | 首次响应延迟、无效重试次数（当前应为 3 → 0） |

**为什么 L0 是"可用"而不是"能用"**：

当前状态下AI **能返回内容**，所以用户看到的是"能用"。但实际每次请求浪费 3 次失败往返，且本地引擎完全没生效。

**这就是"看似可用"的准确含义** —— 它会掩盖 L0 的真实问题。

### 5.3 L1 有据：RAG 引用可溯源

| 项 | 内容 |
|---|---|
| **解决什么** | 每条事实性回答能指到来源；无依据时明说"未找到" |
| **当前状态** | ⚠️ **部分** —— RAG 检索质量好（mrr@10=0.85），但**门控未接入**（AI-P0-3） |
| **达标标志** | ① 事实性回答带可溯源引用；② **无依据时拒答**（而不是硬答）；③ 回答中标明数据来源可信度 |
| **对应批次** | **批次 B**（~140 行） |
| **关键指标** | 依据引用率、**无依据编造率**、拒答正确率（详见 §7.4） |

#### L1 的核心：拒答机制

**当前状态是"检索不到也硬答"** —— 这是幻觉的主要来源。

`retrieval_gate.py` 的三种决策：

| 决策 | 触发条件（阈值） | 行为 |
|---|---|---|
| `abstain` | top1 分数 < 0.60 | **拒答** |
| `retry` | 0.35 ≤ top1 < 0.50 | HyDE / step_back 重试检索 |
| `accept` | top1 ≥ 0.50 | 正常回答 |

**这三种决策目前一个都没生效。**

#### 接入后的预期效果（可验证）

| 指标 | 当前 | 接入后预期 |
|---|---|---|
| `would_abstain` 率 | **未知**（因为没接入） | **应能观测到** —— 这个数字本身就是"AI 有多少问题答不出来"的量化基线 |
| 无依据硬答 | **100%（默认行为）** | 显著下降 |

> **第一批应跑 observe 模式**（现有配置就是 `mode="observe"`），**只记录不拦截** —— 这样可以先拿到"如果切enforce 会影响多少比例的问答"这个数字，**零风险**。

### 5.4 L2 会规划：任务分解与计划生成

| 项 | 内容 |
|---|---|
| **解决什么** | 学习计划由 AI 生成且用户可编辑 |
| **当前状态** | ⚠️ **部分** —— `/api/ai/generate-plan` 端点存在，但 `2027-12-25` 硬编码 5 处（AI-P1-7） |
| **达标标志** | ① 生成的学习计划**节点完整、不与用户已有计划冲突**；② 考期日期来自配置而非硬编码；③ 用户可编辑生成结果 |
| **对应批次** | **批次 B**（B-6 收敛examDate）→ D 批次深化 |
| **关键指标** | 计划完整率、人工修改率 |

#### 一个具体的风险：硬编码考期

`2027-12-25` 被硬编码在 **5 处**（`Dashboard.jsx:72`、`Settings.jsx:137`、`Planner.jsx:395`、`mocks/seed.js:14` + 测试2）。

**2027 考研的实际初试日期未公布**（通常在 2026 年 12 月下旬公布次年日期）。

**后果**：一旦真实日期公布，5 处都要改，**漏改任何一处都会导致倒计时归零或不显示**。

### 5.5 L3 会用工具：Agent + 多轮会话

| 项 | 内容 |
|---|---|
| **解决什么** | 多轮会话不丢上下文；能调用外部工具 |
| **当前状态** | ❌ **不可用** —— `agent.js` 9 端点 8 死（AI-P1-1）；`chat()` 无超时控制 |
| **达标标志** | ① 多轮会话持久化不丢；② **工具调用有超时与失败降级**；③ 用户可中断 |
| **对应批次** | **批次 D** |
| **前置** | **批次 B + C 全部完成** |

#### 一个必须提前处理的工程问题

```javascript
// frontend/src/utils/agent.js:67-76
export function chat(opts) {
  const ctrl = new AbortController()
  ;(async () => {
    const resp = await fetch(`/api/chat`, {   // ★ 原生 fetch，不是 request()
      method: 'POST', ...
      signal: ctrl.signal
    })
```

**它不走 `request()`，因此不受 `client.js:14` 的 `DEFAULT_TIMEOUT=30000` 控制。**

Agent 的工具调用可能长时间无响应 —— **没有超时意味着可能永久挂起**。

**这是从"快速失败"退化成"无限等待"的风险。**

### 5.6 L4 会择校：结构化择校推理

| 项 | 内容 |
|---|---|
| **解决什么** | 推荐结果每条都带数据来源与置信度 |
| **当前状态** | ❌ **不可信** —— 97.29% 数据未核验（AI-P1-2）；择校推荐是 **131 行硬编码 SQL 权重**（§2.10） |
| **达标标志** | ① 每条推荐都带数据来源与年份；② **引用未核验数据时显式提示**；③ 数据不足时**只给区间不给点估计** |
| **对应批次** | **前置：数据治理达标**（§6.7） |
| **关键指标** | 推荐依据可溯源率、拒答率 |

#### 🔴 L4 当前面临的核心障碍不是 AI，是数据

**择校推荐的实际是 131 行硬编码 SQL 权重**（`kaoyan.py:214`），**不走 AI 层，无任何质量门控**。

**这意味着三件事**：

| # | 事实 | 后果 |
|---|---|---|
| **1** | **即使 AI 层全部修好，用户在"智能择校"页看到的也不是 AI 的判断** | 而是一段自始至终没变的 SQL 权重 |
| **2** | **这段公式用的是 97.29% 未核验的数据** | 它给出的排名看起来很确定，实际基础很软 |
| **3** | 🔴 **而它能覆盖的院校只有 217/493（44%）** | **276 所院校根本不在这个公式的考量范围内** —— 用户查冷门院校时，看到的"无推荐结果"实际是"没有数据"，不是"不推荐" |

> **这是一个产品定位问题，必须由用户决策**：
>
> **"智能择校"这个功能名，让用户以为 AI 在做判断。实际是固定公式 + 44% 的院校覆盖。**
>
> **为什么这个信息不对称比技术缺陷更危险**：
>
> - 技术缺陷（页面报错、功能不可用）会**提醒用户"这里有问题"**，用户会绕开或反馈
> - **信息不对称不会提醒任何东西** —— 界面排版专业、结果看起来像模像样，用户会**把它当作 AI 的判断并据此决策**
>
> **一个诚实的固定公式，比一个假装是 AI 的固定公式更安全。**
>
> **选项**：
>
> | 选项 | 内容 | 代价 |
> |---|---|---|
> | A | 改名为"院校匹配" | 诚实，但失去 AI 卖点 |
> | B | 让 AI 真正参与 | 成本高，**且数据未达标前不该做** |
> | **C（推荐）** | **保留公式，但在结果旁标注"基于 N 条数据，其中 M 条未核验，覆盖 X/493 所院校"** | **最低成本，且把信息不对称消掉** |
>
> **注意选项 C 的三段标注缺一不可**：只标"N 条数据"不够 —— 用户会以为没被列出的院校是"不推荐"。**必须明确写出覆盖 X/493**，否则用户仍会误读。

#### L4 的准入门槛（数据治理达标）

**本报告的判断：L4 不应启动，直到数据治理达标。** 理由见 §6.6的"功能危害"论证。

| 门槛 | 当前 | 要求 |
|---|---|---|
| `unverified` 占比 | **97.29%** | **< 60%** |
| **院校覆盖率** | **217 / 493（44.0%）** | **≥ 80%** |
| 官网来源覆盖院校 | **5 / 493（1.0%）** | **≥ 100 所** |
| **采集器功能完整性** | `national_line` **100% 全空** | 该列可正常采集 |
| 年份完整性 | 2022–2025 各 5–7 行 + `year=2099` 脏数据 2 条 | 各年样本量足够且无脏数据 |
| 跨年可比性 | **未测算** | 已测算并确认 |

> **门槛里最容易被忽略的是「院校覆盖率」和「采集器功能完整性」**：
>
> - **覆盖率 44%** 意味着即使 `unverified` 压降到 0%，**仍然有 276 所院校没有任何数据** —— 用户查不到就是查不到
> - **`national_line` 100% 全空** 意味着**有一个功能从未被正确实现** —— 采集器可能还有别的类似缺陷，只是没被发现

### 5.7 每级的准入门槛与降级策略

> **降级策略是最容易被忽略、但最重要的一节。** 当前 `agent.js` 的做法是"静默失败" —— **这是最差解**。

| 级 | 做不到时怎么办 |
|---|---|
| **L0** | 明确报错："AI 服务暂时不可用，请检查后端配置"。**不要静默重试** |
| **L1** | **无依据时明确拒答**："这个资料我没能检索到，库里没有相关内容" —— **而不是编一个** |
| **L2** | 计划生成失败时回退到**模板计划**（现有的固定计划），并告知用户"AI 生成失败，已使用默认计划" |
| **L3** | **工具失败时回退到纯对话并告知**："这个查询工具暂时不可用，我先基于已有信息回答" |
| **L4** | **数据不足时只给区间不给点估计**："A 校近年分数线在 XX-XX 区间（数据来源未核验），建议以官网为准" |

#### 一条应该写进 prompt 的原则

> **降级必须可见。**
>
> 静默降级让用户以为系统正常工作；**可见的降级让用户知道该做什么**（比如"后端未连接，请启动服务"）。

## 6. 数据可信度与 AI 幻觉治理

> **本章是本报告的核心价值。**
>
> 前五章讲的是"AI 怎么修起来"，本章讲的是"**修起来之后怎么保证它说的是真的**"。
>
> **如果只能保留一章，应该是本章。**

### 6.1 问题的真实规模：97.29% 意味着什么

#### 实测数据（本报告独立复核）

| 项 | 实测值 | 查询 |
|---|---|---|
| `kaoyan_scorelines` 总数 | **811** | `SELECT COUNT(*) FROM kaoyan_scorelines` |
| ├ `unverified` | **789** | **97.29%** |
| ├ `school_official` | 16 | 1.97% |
| └ `csv_sample` | 6 | 0.74% |
| `kaoyan_admissions` 总数 | **832** | `SELECT COUNT(*) FROM kaoyan_admissions` |
| ├ `txkyer.cn`（**第三方，非官网**） | **825** | **99.16%** |
| └ `csv_sample` | 7 | 0.84% |
| 院校总数 | **493** | `SELECT COUNT(*) FROM kaoyan_schools` |
| **有分数线的院校** | **217**（**44.0%**） | `COUNT(DISTINCT school_id) FROM kaoyan_scorelines` |
| **`school_official`覆盖院校** | **5**（**1.0%**） | `COUNT(DISTINCT school_id) WHERE source='school_official'` |
| 自建采集器产出 | **空数组** | `datasource_registry.json` 的 `custom` |
| `verified=1` 的题目 | **0 行** | — |
| `ai_generated=1` 的题目 | **288 行** | — |

#### 关键澄清：97.29% 这个数字的三个层次

**层次 1：数字本身**
`unverified` 占 `kaoyan_scorelines` 的 97.29%（789/811）。**这个数字准确。**

**层次 2：口径要说明**
如果把 `admissions` 也算进来，"未标为 `school_official`"的比例是 789/1643 = **48.0%**。

**但这不是好消息** —— 因为 `admissions` 标的是 `txkyer.cn`（第三方考研网站），**它同样不属于已验证来源**，只是没用 `unverified` 这个标签。

> **正确表述**：**择校数据几乎全部来自未经验证的第三方聚合源。**
>
> **错误表述**："只有 2.71% 未验证" —— 这是按标签算的，会严重低估问题。

**层次 3：真正的问题比比例更严重**
- **493 所院校里只有 217 所（44%）有分数线**
- **`school_official`（唯一可信来源）只覆盖 5 所（1%）**
- **自建采集器从未产出过任何数据**（`custom` 是空数组）
- **825 条招生数据全部来自 txkyer 单一源**，无任何交叉验证

> ### 这三条为什么比 97.29% 更重要
>
> **比例说明"这些数据不可信"，覆盖率说明"连数据都没有"。**
>
> 对用户的实际影响：
> - 查"贵州大学电子信息"→ 有数据，但 97% 可能是错的
> - 查"某某冷门院校" → **根本没有数据**（276 所院校没有分数线）
> - **用户无法区分这两种情况** —— 界面上一视同仁

#### 🔴 层次 4：比"来源不可信"更严重的问题 —— 绝大多数院校根本没数据

> **这一节是 §6.1 里最该被记住的事实。**

**实测覆盖率数据（`database/kaoyan.db`）：**

| 项 | 实测值 | 覆盖率 |
|---|---:|---:|
| 院校总数（`kaoyan_schools`） | **493** 所 | 100% |
| **有分数线的院校** | **217** 所 | **44.0%** |
| **`source='school_official'` 的院校** | **5** 所 | **1.0%** |
| **无任何分数线的院校** | **276** 所 | **56.0%** |
| 自建采集器产出（`datasource_registry.json` 的 `custom`） | **空数组** | **从未产出** |

**这个对比揭示的问题比 97.29% 严重得多**：

| 维度 | 说明的是 | 严重度 |
|---|---|---|
| 97.29% `unverified` | **有数据，但不可信** | 🔴 高 |
| **44% 覆盖率** | **一半以上院校连数据都没有** | 🔴🔴 **更高** |

**对用户的实际影响**：

```
查"贵州大学 电子信息"
  → 有数据 ✅
  → 但 97% 可能来自未核验的第三方聚合源 ⚠️
  → 用户能看出有数据，但不知道能不能信

查"某某冷门院校"
  → 根本没有数据 ❌
  → 界面可能显示空白，或显示"0"
  → ★ 用户无法区分"没有数据"和"数据是0"
```

```
total_line      0/811 空  →  ✅ 100% 采到

```

**同一张表、同一个采集器、同一批数据，两个字段的成功率是 0% 和 100% 的两极。**

**这说明的不是"采集率偏低"，而是"采集器的某个功能从未被正确实现"。**

| 假设 | 判别依据 | 结论 |
|---|---|---|
| "数据源本身缺国家线" | 若如此，`total_line` 也该缺 | ❌ 排除 —— `total_line` 100% 采到 |
| "采集器整体失败" | 若如此，所有字段都该空 | ❌ 排除 —— 13% 空值率普遍存在 |
| **"国家线采集功能未实现/已损坏"** | **单字段两极分化** | ✅ **最可能** |

**这个判断的方法论价值**：

> **当一个数据集里出现"某列 100% 空、某列 100% 满"的极端分化时，几乎可以断定是代码缺陷而非数据缺失。**
>
> **因为真实世界的"数据源没有这个字段"和"采集器没采这个字段"，在统计上会长得完全不一样** —— 前者会伴随其他字段的普遍缺失，后者只会表现为孤立的单列全空。
>
> **所以：看到整列全空，第一反应应该是"查代码"，而不是"查数据源"。**

**建议动作**：检查 `kaoyan` 采集器中处理国家线的代码路径（很可能从未被调用，或解析逻辑恒返回 None）。**这是定位采集器缺陷的最短路径。**

### 6.2 幻觉的三条具体产生路径

> **必须给路径，不能只给定义。** 因为每条路径的拦截手段完全不同。

#### 路径一：检索幻觉

**机理**：RAG 召回的 chunk 与问题无关 → 模型仍然硬答。

**为什么门控是针对性的拦截**：`retrieval_gate.py` 的 `abstain` 决策正是为拦截这条路径设计的 —— 当 top1 分数 < 0.60 时判定"检索结果不可用"。

**当前状态**：❌ **门控未接入主链路**（AI-P0-3）。

**好消息**：`/api/gate/search` **实测可用**（`decision:"accept"`, `top1_score:70.16`, `top1_margin:15.17`, `distinct_doc_count:3`）—— **只需接线，无需重写**。

**拦截手段**：接入 `evaluate_gate()`，`abstain` 时走拒答话术。

#### 路径二：数据幻觉（最危险）

**机理**：召回内容本身"正确"（确实来自知识库），**但内容本身是错的**（来源未核验）→ 模型**忠实地把错数据讲得更自信**。

**这一条最危险，因为它绕过了所有现有的防护**：

| 防护机制 | 为什么挡不住 |
|---|---|
| RAG 检索质量高（mrr@10=0.85） | ✅ 检索确实找到了相关内容 —— 但内容本身是错的 |
| 内容安全拦截（19 条正则） | ✅ 没有敏感词 —— 只是数据不准 |
| `_route_query` 路由 | ✅ 路由正常 —— 问题不在路由 |
| **`SourceBadge` 角标** | ⚠️ **只影响界面显示，不影响 AI 输出** |

**具体路径**（实测确认）：

```javascript
// KaoyanAssistant.jsx:49-62

//    ↓ 查询 kaoyan_scorelines（97.29% unverified）
// ② 把引擎结论喂给 aiApi.chat() 做"AI 深度解读"
use_rag: false      // :56  ← ★ RAG 被关闭，没有检索兜底
// ③ AI 以更流畅自信的语气复述这些结论
```

**用户在界面上无法区分"引擎基于真实数据"与"AI 基于未验证数据"。**

**拦截手段**：
1. **AI 输出侧强制标注**（§6.5）—— 引用未核验数据时必须在回答里说明
2. **入口侧标注**（§6.3）—— `SourceBadge` 已实现，需扩展到 AI 路径
3. **数据侧治理**（§6.7）—— 压降 `unverified` 比例

#### 路径三：前提幻觉

**机理**：system prompt 硬编码了错误的前提 → **AI 基于错误前提回答，且回答看起来完全正常**。


**AI 回答**：基于"贵州大学电子信息专硕"的前提

**为什么这条最隐蔽**：用户不会看到任何异常 —— 回答的语气、格式、逻辑全部正常，只是**前提错了**。

**grep 统计**：`贵州大学` **14 处**命中（前端 6 + 后端 5 + 测试 2 + 注释 1）。

**拦截手段**：prompt 动态注入（批次 B-2）。

### 6.5 治理手段三：输出侧 —— 置信度标注与拒答

#### 三档输出策略

| 档位 | 触发条件 | 输出策略 | 示例 |
|---|---|---|---|
| **可直接给结论** | 数据 `school_official` + 有检索依据 | 正常回答 + 引用 | "贵州大学 2024 电子信息复试线为 XXX（来源：学校官网）" |
| **需标注后给** | 数据 `unverified` / `txkyer.cn` | 回答 + **强制标注** | "根据平台收录数据，XX 大学近三年分数线在 XX-XX 区间。**注意：该数据来自第三方聚合，未经过官网核验，建议以官网公布为准**" |
| **应拒答** | 检索分数 < 0.60 或数据完全缺失 | **明确拒答** | "这个资料我没能检索到，库里没有相关内容。**建议直接查询目标院校官网**" |

#### 强制标注的实现方式

**方案 A（低成本，推荐先做）**：在 prompt 里要求

```
如果引用的数据 source 不是 school_official，必须在回答末尾追加：
"数据来源：第三方聚合，未核验"
```

**方案 B（更可靠）**：在输出层做后处理

```python
# 伪代码示意
def annotate_source(answer, cited_records):
    if any(r.source != 'school_official' for r in cited_records):
        return answer.rstrip() + "\n\n⚠️ 数据来源：第三方聚合，未核验。建议以院校官网公布为准。"
    return answer
```

**方案 B 的好处**：不依赖模型"自觉"，是**代码层的保证**。

> **本报告倾向方案 B** —— 因为§6.6 的第一条路径已经证明了：**依赖模型自觉是不可靠的**，数据本身可能"正确"但来源不可信，模型不会意识到自己需要标注。

#### 拒答的话术设计

**拒答不等于"我不知道"** —— 应该给出下一步：

| ❌ 差的拒答 | ✅ 好的拒答 |
|---|---|
| "抱歉，我无法回答这个问题。" | "知识库里没有检索到这个问题的相关内容。**你可以：① 换更具体的关键词再问；② 直接查询院校官网；③ 把相关资料上传到文档知识库后重试**" |

**好的拒答让用户知道下一步做什么，而不是让用户以为 AI 坏了。**

### 6.6 治理手段四：兜底 —— 拒答优于编造

> ## 🔴 本节是 §6 的核心结论之一：趋势类功能当前不应做
>
> **这一条是硬约束，不是建议。**
>
> 下面这段判断是本报告在 AI 域最有价值的洞察之一 —— 它区分了两种看起来相似、但危害完全不同的情况。

#### 核心原则

> **一个诚实的"这个数据来源未核验，我不能给你建议"，比一个自信的错误答案有价值得多。**
>
> **尤其在择校这个域 —— 错误建议的代价是用户损失一年时间与金钱。**

#### 🔴 一个必须明确的判断：趋势类功能当前不应做

**历年趋势分析（2022–2025）的 4 项前置条件当前全部不满足**：

| 前置条件 | 当前状态 | 判定 |
|---|---|---|
| 各年样本量 | 2022–2025 各 **5–7 行** | ❌ 样本量严重不足 |
| 数据可信度 | `unverified` **97.29%** | ❌ |
| 无脏数据 | **`year=2099` 2 条** | ❌ |
| 跨年可比性 | **未测算** | ❌ |

**趋势图 = 1 个真点 + 4 个噪声点。**

> ### 这是"功能危害"而不是"功能缺失"（本章最重要的一次区分）
>
> **功能缺失**：用户点进去发现没有数据 → 会自己找别的方法 → **无害**
>
> **功能危害**：用户看到一条趋势线 → **基于噪声做择校决策** → **有害**
>
> 这两者的差别不在数据量，在**用户的下一步动作**：
>
> | | 功能缺失 | 功能危害 |
> |---|---|---|
> | 用户看到 | "暂无数据" | 一条看起来专业的趋势图 |
> | 用户的判断 | "这个功能没数据，我去官网查" | "这所学校分数线在涨，我应该报" |
> | 用户下一步 | **去核实** | **去决策** |
> | 错误代价 | 时间成本 | **一年时间与金钱** |
>
> **所以本报告的硬约束**：**在数据治理达标前，AI 不得输出任何跨年趋势结论。**
>
> 这不是"保守"，是**拒绝提供会误导决策的信息**。
>
> 这不是"保守"，是**拒绝提供会误导决策的信息**。

**对应的 prompt 约束**：

```
【禁止项】
6. 不得输出跨年趋势结论（如"近三年分数线呈上升趋势"）——
   当前数据年份样本量不足，趋势不可靠。
   如用户问趋势，明确说明"数据不足以支撑趋势分析"。
```

```
   │      让不可信可见 —— 用户的知情权
   ↓
   │← 接入官网白名单机制（6-8 人时）
   │      unverified 开始真实下降
   ↓
   │
< 60%  ← 中期目标
   │
   │← 持续治理
   ↓
< 30%  ← 长期目标
   │
   ↓
 可信 → L4「会择校」才具备启动条件
```

> **这个刻度图传递一个关键判断**：
>
> **让用户看见不可信（B-3，成本最低）与压降不可信（白名单机制）是两件事，必须并行做。**
>
> - **先看见**：用户至少知道自己看到的是软数据 → **信任从"被误导"转为"知情"**
> - **再压降**：数据质量真正提升 → **产品价值真正提升**
>
> **只做前者不改变产品价值，但能立刻止损信任危机。只做后者，用户在压降完成前仍被误导。**

## 7. 评估体系

### 7.1 为什么"看起来变好了"不算评估

> **本报告拒绝把"AI 回答变长了 / 格式变好了 / 语气变自然了"当作改善。**

#### 模型有随机性

同一个问题两次回答可能不同。**单次对比无法区分"改好了"与"这次运气好"。**

#### 用户无法判断答案对错

用户不知道"贵州大学电子信息 2024 复试线该是多少"。**所以"用户觉得回答不错"完全不能作为质量证据。**

#### 因此必须先建立可自动判定的评测集

**没有评测集之前，所有"变好了"的判断都是主观的** —— 而这恰恰是 AI 项目最容易陷入的陷阱：改了一堆prompt，LLM 主观感觉"好像更聪明了"，但没有任何数据支撑。

### 7.2 三层评估：能力 / 质量 / 回归

| 层 | 评什么 | 怎么评 | 门禁 |
|---|---|---|---|
| **能力层** | 能不能做（链路通不通、流式是否正常、多轮是否丢上下文） | 接口级自动化测试 | **不允许断链回归** |
| **质量层** | **答得对不对、有没有依据** | **评测集 + 人工/模型判分** | **关键项不达标即阻断发布** |
| **回归层** | 改 prompt / 换模型会不会让别处变差 | 评测集重跑 + 前后对比 | **任何指标退化 > 阈值即阻断** |

#### 三层的必要性

**只有能力层是不够的** —— 因为"能返回内容"这个断言太弱（§7.4 会详细说明这个陷阱）。

**只有质量层是不够的** —— 因为改 A 场景的 prompt 可能破坏 B 场景。

#### ⚠️ 一个必须避免的陷阱：能力层测试会给出虚假的安全感

**如果只测"能否拿到响应"，会出现这样的假绿**：

```python
# ❌ 弱的断言
assert response.status_code == 200
assert len(response.text) > 0# 只证明有内容
```

**AI-P0-1（`force_local` 仍返回内容）会完整通过这个测试** —— 因为 NameError 被吞后降级成功，**响应完全正常**。

**结论：能力层的测试必须断言"走的是哪条路径"，而不只是"有没有响应"。**

### 7.3 评测集建设（最小可行规模）

#### 不追求规模，先做 50 条

| 类别 | 条数 | 覆盖内容 |
|---|---:|---|
| **择校问答** | **15** | 分数线查询、院校对比、录取人数、"XX 校值得报吗" |
| **错题分析** | **10** | 错因诊断、同类题识别、复习优先级 |
| **学习规划** | **10** | 今日任务、时间分配、进度落后怎么办 |
| **知识库检索** | **10** | 教材概念（卡诺图、时序逻辑…）、公式推导 |
| **拒答场景** | **5** | 库里没有的问题、越界问题、数据不足的趋势问题 |
| **合计** | **50** | — |

#### 每条必须标注"正确答案依据来自哪里"

**这是最关键的设计要求**：

```json
{
  "id": "kaoyan-001",
  "question": "贵州大学电子信息专硕的复试线是多少？",
  "category": "择校问答",
  "expected": {
    "must_include": ["分数线", "年份"],
    "must_have_source": true,         // ← 必须带来源
    "source_hint": "kaoyan_scorelines WHERE school_id=..."
  },
  "forbid": [
    "给出跨年趋势结论",                // ← §6.6 的禁止项
    "无任何来源标注的分数线数字"
  ],
  "should_abstain": false
}
```

**为什么"标注依据"比"标注答案"更重要**：

**因为 AI 的答案表述可以千变万化，但"有没有依据"是客观可判定的。**

如果只标注标准答案，评测就会退化成"逐字对比" —— 这既不现实（模型表述本来就多样），也会逼着开发者去调prompt 让模型输出固定格式，**而不是真的提高质量**。

#### 与 L1 的"有据"要求同源

**一份工作两处收益**：评测集的"标注依据"和 L1 的"引用可溯源"是同一个要求的两面。

**§6.5 建议的方案 B（输出层强制标注）正好让评测变得可自动化** —— 因为标注是代码做的，评测时可以直接解析标记，不需要人工判断。

### 7.4 关键指标与目标值

| 指标 | 定义 | 当前 | 目标 | 测量方法 |
|---|---|---|---|---|
| **依据引用率** | 事实性回答中带可溯源引用的比例 | **[待建立基线]** | ≥ **90%** | 评测集自动判（方案 B 的标记可直接解析） |
| **无依据编造率** | 无依据却给确定性结论的比例 | **[待建立基线]** | ≤ **5%** | 评测集 + 人工抽检 |
| **拒答正确率** | 应拒答时正确拒答的比例 | **不适用**（当前无拒答机制） | ≥ **95%** | 评测集的 5 条拒答场景 |
| **死接口数** | 前端调用不存在后端端点的数量 | **8**（9 个中 1 个存活） | **0** | 契约测试（见下） |
| **`force_local` 生效** | 请求强制 local 时 `engine_used` 是否为 `local` | **❌ 否** | **✅ 是** | **单条断言即可** |
| **择校数据 `unverified`** | — | **97.29%** | **< 60%**（中期） | SQL 直接查 |
| **无效降级重试次数** | 因无 key 导致的必然失败次数 | **3 次/请求** | **0** | 日志计数 |
| **趋势类越权输出** | 在数据不达标时输出趋势结论 | **[待建立基线]** | **0** | 评测集 + prompt 约束 |

#### 两个"当前值"的诚实说明

| 指标 | 为什么标 [待建立基线] |
|---|---|
| 依据引用率 | **因为门控未接入、AI 输出无来源标记，所以这个指标当前无法测量** —— 必须先做批次 B 才有意义 |
| 无依据编造率 | 同上，且需要人工判分才能确认"是否编造" |

> **这不是"没测"，是"测不了"** —— **先做批次 B，指标才有可测性。**
>
> **这与《改进报告》§6 的"测试架构对某类缺陷无感知"是同一个问题**：不是不想测，是当前的系统结构让这个指标无法被定义。

#### 契约测试（可直接落地，成本极低）

**参照《改进报告》§6.4 的方案** —— 那个报告里已有一个正确的范式：

```javascript
// 扩展 client.contract.test.js 的思路（前端）
// 遍历所有前端 api 封装调用的路径，与后端路由清单快照比对
const FRONTEND_CALLS = [
  '/api/agent/test',      // ← 应标记为"后端不存在"
  '/api/agent/auth',
  '/api/sessions',
  '/api/chat',
  // ...
]
// 断言：调用不存在端点的清单必须为空
```

**当前这个测试会立刻变红** —— 因为有 8 个死接口。

**把"已知例外"显式写进白名单**，任何新增的未实现端点都会让测试失败。

**成本：~30 行；收益：永久防止死接口再次出现。**

### 7.5 回归门禁与 CI 接入

#### 门禁规则

| 规则 | 说明 |
|---|---|
| **1. 改 prompt 必须重跑评测** | 无例外 |
| **2. 换模型必须重跑评测** | 无例外 |
| **3. 调 RAG 参数（阈值、top-k、权重）必须重跑评测** | 无例外 |
| **4. 关键指标退化超 5% 即阻断** | 防止"改好了一个场景，毁了两个" |
| **5. 死接口数必须 = 0** | 契约测试硬门禁 |
| **6. `force_local` 必须生效** | 单条断言 |

> **⚠️ 门禁指标必须是"有依据率"与"编造率"，不能是"回答长度"或"调用次数"** ——
>
> **后者会激励刷指标**。比如"让 AI 多引用几个来源"很容易做到，但**如果只看引用数量，AI 可以引用不相关的来源来刷分**。**必须校验引用的相关性。**

#### 抽样人工判分（模型判分不可全信）

**建议：LLM 自动判分 + 人工抽检 20%**

| 项 | 说明 |
|---|---|
| **LLM 判分** | 适合"格式是否符合""是否包含必需信息""是否触发了禁止项" |
| **人工判分** | 适合"这个答案对不对""这个引用是否真的支持结论" |
| **为什么不能全用 LLM 判分** | LLM 判分本身也会被"看起来很详细但错误"的答案骗过 —— 这与被测系统是同类问题 |

#### 当前测试基线（可作为起点）

```

```

**这202 个测试已覆盖 `model_registry.py`（33 个）、`llm_output.py`（4 个）等。**

**但必须注意**：`lora_finetune/eval_result.json` **只测了 3 条**（`limit: 3`）且 `compare: false`（**未与基座对照**）。

**所以目前的状况是**：单元测试做得不错，**但端到端的 AI 质量评测基本不存在。**

### 7.6 评估的诚实边界

#### 三个必须承认的局限

| 局限 | 说明 | 缓解 |
|---|---|---|
| **评测集本身会有偏** | 由项目自己出题，考的可能都是自己擅长的 | 引入真实用户提问作为补充样本 |
| **模型随机性需要多次采样** | 单次判定不成立 | 每个 case 跑 3次取中位数，或用 pass@k / consistency 指标 |
| **成本与延迟指标待补齐** | 首字延迟、token 成本、并发上限 | 🔶 `[待核实]` —— 本轮未实测 |

> **关于第三条**：AI 调查报告中未包含性能与成本的实测数据（首字延迟、token 消耗、并发能力）。
>
> **本报告不编造这些数字。** 建议在批次 A 完成后补一次基线测量 —— 因为**修掉 NameError 后本地引擎生效，首字延迟会显著变化**，这个数字是评估批次 A 效果的重要依据。

#### 一个容易被忽略的风险：评测集会成为优化目标

**如果评测集固定，开发者会不自觉地针对它调优** —— 导致：
- 评测分数上升，但真实体验没改善（过拟合评测集）
- 评测集与真实使用场景脱节

**缓解**：
1. 评测集定期更新（加入真实用户提问）
2. 保留一个**不参与调优的 holdout 集**
3. 人工抽检的样本**不告知开发者具体题目**

| **NameError** | Python 内置异常，引用未定义变量时抛出；会被 `except Exception` 捕获 |
| **strangler（绞杀者）模式** | 先加新路径、再逐个切流、最后删旧路，避免一次性重构 |
| **RAG** | 检索增强生成：先从知识库检索相关内容，再让模型基于检索结果回答 |
| **FTS5** | SQLite 的全文检索扩展，本项目用它做关键词检索 |
| **RRF** | Reciprocal Rank Fusion，融合多路检索结果的排序算法 |
| **bge** | 本项目使用的向量嵌入模型（bge-small-zh-v1.5，512 维） |
| **recall@k / mrr@k** | 检索质量指标；`mrr@10` 比 `recall@10` 更稳健 |
| **abstain / 拒答** | 检索结果不可用时明确说不知道，而不是编造 |
| **`would_abstain` 率** | 门控在 observe 模式下预估的"应该拒答"比例 |
| **依据引用率** | 事实性回答中带可溯源引用的比例（本报告提出的核心指标） |
| **无依据编造率** | 无依据却给确定性结论的比例（越低越好） |
| **功能危害** | 功能存在但会导致用户做错决策 —— 比功能缺失更危险 |
| **source=unverified** | 该条数据来源无法追溯到官方，是"不可信"的标记 |
| **`school_official`** | 唯一可信的来源标记（当前仅 16 条 / 5 所院校） |

## 结语：三句话总结

1. **最严重的问题是"看似可用，实则失效"**：`ai_router.py:368` 一行变量名写错，让本地引擎 100% 失效；云端 3 个服务商全部无密钥；质量门控写好了却没接线。**三者叠加，AI 对话链路实际上是完全不通的，而界面上看不出来。**

2. **基础设施比表面看起来好**：RAG 检索链路 mrr@10 = 0.85、召回真·教材；25,815 条 bge 向量；`model_registry.py` 33 个测试全绿；内容安全 19 条正则先于模型调用。**问题不是"从零建设"，是"接上 + 收口 + 补可信度约束"。**

3. **最该立刻做的是两件事**：**修 `ai_router.py:368` 的一行变量名**（本地引擎从 0% 变 100% 生效），**接入已经写好的 `retrieval_gate`**（让 AI 敢说"没找到"）。合计约 170 行改动，能把"看似可用"变成"真的可信"。
