# 36-公式修复落地报告（2026-10-21）

> 目标：让考研题库里被丢弃/读错的数学公式，重新变成机器可读的 LaTeX
> 结论：**docx 与 PDF 两条链路全部打通，全程零 GPU、零联网、零额外下载**

---

## 1. 问题是什么

入库管线原来只取 `paragraph.text`，而 Word 题库里的公式**是图片**，于是：

```
原文：设 {x_n} 是数列，下列命题中不正确的是（  ）
入库：2．设是数列，下列命题中不正确的是（　　）．      ← 公式消失
      A．  B．  C．  D．                            ← 选项全空
      【解析】因为                                  ← 后半句没了
```

扫描版 PDF 更糟：RapidOCR 对公式是「**读错**」而不是「漏读」：

```
f(x)        → f(α) / f(r) / f(z)
f(-x)=f(x)  → f（一）=f()
f(g(x))     → fLg(）
```

错字原样入库，LLM 读到的是**错误的数学式**——比缺公式更危险。

规模（实测）：

| 载体 | 文档 | 污染块 | 机制 |
|---|---|---|---|
| PDF（扫描件） | 454 | **6,077** | OCR 读错 |
| .docx | 28 | **1,298** | 公式图被丢弃 |
| .doc | 1 | 1 | 二进制格式 |
| 合计 | 483 | **7,376 / 20,676 = 35.7%** | |

## 2. 最终方案：复用本机已有的 ONNX 模型

### 走过的两条错路（记录以免重试）

1. **pix2tex（LaTeX-OCR）**：依赖 `pytorch-lightning` → `albumentations` →
   `skimage` → `albucore` → `numkong`，本机反复装不上；且对中文公式是盲区。
2. **MinerU 2.7.6 pipeline**：要 torch 版 `PDF-Extract-Kit`，而 `D:\平台\.venv-ocr`
   是 **CPU 版 torch**（2.14.1+cpu）。实测单页 Layout 9.6s → 公式检测 7.4s →
   公式识别阶段**卡在第 16/28 张超 2 分钟**。换 CUDA torch 要重下 2.5GB。

### 走通的路

本机 MinerU 4.x 落盘了一套 ONNX 模型（819MB），其中两块直接可用：

| 模型 | 路径 | 用途 |
|---|---|---|
| `PP-DocLayoutV2` | `~/.mineru/models/MinerU-4_models_onnx/Layout/PP-DocLayoutV2/inference.onnx` | 版面检测（204MB） |
| `PP-FormulaNet_plus-M` | `.../MFR/pp_formulanet_plus_m/PP-FormulaNet_plus-M.onnx` | 公式识别（591MB） |

加上 PyMuPDF 渲染，就是完整链路：

```
docx ──▶ services/docx_formula.py 抽取内嵌公式图 ──┐
                                                  ├─▶ services/formula_latex.py ──▶ LaTeX
PDF ──▶ 渲染 200dpi ──▶ 版面检测 ──▶ 裁切公式框 ──┘
```

**全部 onnxruntime CPU 可跑，tokenizer 内嵌在模型配套 yaml 里，不需要下载词表。**

## 5. 五个必须记住的实现细节

这些都是踩过坑才对的，改代码前先读：

### 5.1 透明底 GIF 必须显式合成白底

Word 公式图大量是带 alpha 的 GIF。直接 `convert("RGB")` 会把透明处变**黑**，
「白底黑字」变「黑底黑字」——实测一张 144×47 的完整公式被识别成 `\cdot`。

### 5.2 WMF/EMF 必须直接拒绝

PIL 的 `WmfImagePlugin` 只能读尺寸和部分记录，渲染出的位图**内容失真**：
一份数电讲义的逻辑代数公式（`0·1=0`、`A·A=A`）被识别成几何符号
`\angle A B C`、`\Delta A \cong \Delta B D`。语法合法、语义全错，
**比不识别更糟**。所以 `.wmf/.emf/.wmz/.emz` 直接判不可渲染。

### 5.3 极扁图会拖死整批

`240×15` 这类单行下标图（`x_{n+1}`）实测识别要 **21.8s**（正常 0.3s），
且模型对极扁输入吐残缺序列。识别器层 `MAX_ASPECT=12` 快速失败（不跑推理）。

### 5.4 版面检测的预处理和坐标都不能照抄直觉

- 预处理严格照模型自带 `inference.yml`：`mean=[0,0,0] std=[1,1,1]` +
  **直接拉伸 800×800（不 letterbox）**。按 ImageNet mean/std 做会得到错误的框。
- **Raw 输出坐标已是原图像素**，不要再按 800/原图反算。
  实测 1654×2339 页面，raw x∈[84,1567]、y∈[68,1941]，正好在图内；
  反算会溢出到 5270。
- 裁切要**外扩 2–4px**，否则会切掉分式横线和积分号。

### 5.5 判别公式图用绝对尺寸，不要用宽高比

`min_formula_aspect=1.2`（宽高比低于 1.2 判为电路图）是**错的**——短公式
本身就是近方形的，实测误杀 766 个真公式：

```
27×24 → \{x_n\}     17×41 → \frac{\pi}{2}    22×24 → \overline{S}_n
72×74 → \begin{bmatrix}1&0&0\\0&1&0\end{bmatrix}
```

正确判据：公式图高度 12–160px，电路图/波形图通常 >160px。
用 `--max-formula-height 160` 就够，加上 `--min-formula-side 4` 丢段落装饰。

## 6. 怎么用

```powershell
cd D:\平台\backend-main-fastapi

# 干跑（默认，不写库）
.venv\Scripts\python.exe scripts\backfill_docx_formulas.py --all-docx
```

```powershell
# 单份，指定页
.venv\Scripts\python.exe scripts\extract_pdf_formulas.py --pdf "某真题.pdf" --pages 25,26

.venv\Scripts\python.exe scripts\extract_pdf_formulas.py --top-polluted 5 --max-pages 2

# 导出裁图 + JSON 报告
.venv\Scripts\python.exe scripts\extract_pdf_formulas.py --pdf x.pdf --crops temp\crops --report r.json
```

## 8. 已知限制（据实记录，不要以为已经完美）

### 8.1 回填位置有局部错位

docx 里的公式图是**浮动锚点**（`w:drawing` 挂在某个 run 上，但视觉位置可能
不在那里）。`docx_formula.py` 按 body 顺序抽取，所以顺序大体正确，
但会出现：

- **连续多个 LaTeX 紧挨**：`$D_f$$D_g$$\overline{...}$`——原文那里确实是
  连续几个公式图，中间没有文字，所以没有分隔符；
- **局部空洞**：`它的定义域为，u称为中间变量`——这里本该有公式，但那张图
  被尺寸/宽高比过滤掉了，走的是「保留占位符」或直接被跳过。

实测抽样：位置正确的占多数，紧挨和空洞是少数。**没有做系统性的位置校验**，
所以不能声称「每一处都在正确位置」。

### 8.2 覆盖率是「块内公式处数」口径

93.9% 指的是「已识别成 LaTeX 的处数 / (LaTeX 处数 + 图片兜底处数)」。
它**不**衡量位置准确性，也不包含被过滤掉（略扁/略高/略大）的那些图。

### 8.3 部分块没能重跑

doc 34/36 第二轮修复块数少于第一轮（55→41、42→40）。原因是个别块的首尾
被第一轮写坏（不配对的 `$`），连前缀定位也对不上。这些块保留第一轮的版本。
**质量优先于覆盖面**——没有为了凑数去强行匹配。

见下一节第 1 条。
