## 三、问题清单

### [P0] 生产构建会清空后端正在服务的线上目录，失败时可能导致站点不可用

- **位置**：`D:/平台/frontend/vite.config.js:26-27`
- **现象**：`outDir: '../backend-main-fastapi/static'` 配合 `emptyOutDir: true`。每次 `npm run build` 都会**先递归删除后端的线上静态资源目录**，再写入新产物。本次构建在删除阶段因文件被占用而中断。
- **影响**：
  - **对用户**：这是最坏情况。若删除成功但写入失败（例如磁盘满、构建中途报错），后端仍在 :8000 对外服务，但 `index.html` 与 `assets/` 已被删空 → **访问即白屏**。当前项目「一个目录同时是源码的输出目标和运行中的生产环境」，没有任何回滚保护。
  - **对构建**：后端只要在运行（当前 PID 57116 正在监听 8000），`npm run build` 就可能因文件占用而失败，构建流程不可靠、不可重复。
  - **对维护**：`vite.config.js:25` 的注释坦承这是为了「消除版本漂移」而做的取舍，但代价是把构建产物和线上服务耦合在了一起。
- **证据**：
  ```
  error during build:
  [safe-delete] 操作失败: ERROR D:\平台\backend-main-fastapi\static\index.html:
    Error during a `trash` operation: Os { code: -2147024894,
    description: "windows error: 系统找不到指定的文件。 (0x80070002)" }
      at emptyDir (.../vite/dist/node/chunks/dep-BK3b2jBa.js:17082:19)
      at prepareOutDir (.../vite/dist/node/chunks/dep-BK3b2jBa.js:65746:7)
  ```
  后端确实在运行：`TCP 0.0.0.0:8000 LISTENING 57116`
- **建议**：**构建输出与线上服务目录解耦**。推荐 `outDir: 'dist'`（项目已有该目录，且已在 `.gitignore` 中），构建成功后再由部署步骤拷贝到后端静态目录；或至少保留 `dist` 产物、拷贝而非直写。若坚持直写，必须改成「先构建到临时目录 → 整体原子替换」，避免出现目录被清空而产物未就绪的中间态。

### [P1] `EChart` 组件卸载时移除的是另一个函数，resize 监听器持续泄漏

- **位置**：`D:/平台/frontend/src/components/EChart.jsx:52-58`
- **现象**：
  ```jsx
  const handler = () => chartRef.current && chartRef.current.resize()
  window.addEventListener('resize', handler)      // 注册 handler
  ...
  window.removeEventListener('resize', () => {})   // 移除了一个全新的匿名函数
  ```
  卸载时传入的是**新建的匿名函数**，与注册的 `handler` 不是同一引用，移除操作**完全无效**。
- **影响**：
  - **对用户**：考研分析页（`KaoyanAnalysis` / `KaoyanCompare` / `KaoyanMap` / `KaoyanScatter` / `KaoyanSchoolDetail`）每次进出都会向 `window` 永久追加一个 resize 监听器，且每个闭包都持有 `chartRef` → **已销毁的 ECharts 实例无法被垃圾回收（内存泄漏）**。长时间反复切页后内存持续上涨，移动端低配机可能卡顿甚至崩溃。
  - **对维护**：写法极具误导性——看起来做了清理，实际没做，后续排查内存问题会很痛苦。
- **证据**：见上方代码；`components/EChart.jsx:56` 与第 53 行注册的 `handler` 无任何引用关系。
- **建议**：改为 `window.removeEventListener('resize', handler)`；同时在卸载时置空 `chartRef.current = null`，并补充 `chart.off('resize', handler)`（ECharts 自身也注册了 resize 处理）。

### [P1] `parser.js` 同时静态与动态导入 pdfjs，代码分割完全失效

- **位置**：`D:/平台/frontend/src/utils/parser.js:1-2`（静态）与 `parser.js:32-33`（动态）
- **现象**：文件顶部已静态导入 `pdfjs-dist` 和 worker，第 32-33 行又在 `parsePdf()` 内部动态 `import()` 同一模块。构建期明确告警：
  ```
  (!) .../pdfjs-dist/build/pdf.mjs is dynamically imported by
      .../src/utils/parser.js but also statically imported by
      .../src/utils/parser.js, dynamic import will not move module into another chunk.
  (!) .../pdfjs-dist/build/pdf.worker.min.mjs?url is dynamically imported by
      .../src/utils/parser.js but also statically imported by
      .../src/utils/parser.js, dynamic import will not move module into another chunk.
  ```
  第 31 行注释写着「仅在真正解析 PDF 时引入 pdfjs，降低首屏主包体积」——**意图与实现相反**。
- **影响**：
  - **对用户**：pdfjs 无法独立成块，会被并入 `parser` chunk（实测 **863.90 kB**），连带 worker（**1,375.84 kB**）也无法按需加载。用户即便只用 markdown/txt 解析，也会背上这部分体积。
  - **对构建**：每次构建固定产生 2 条 Rollup 告警，属于「已知但长期不管」的技术债。
- **证据**：构建输出原文见上；产物 `parser-HpoMIFMP.js` 863.90 kB / gzip 239.61 kB。
- **建议**：删除顶部的静态 `import`（第 1-2 行）与 `GlobalWorkerOptions` 初始化（第 6 行），把 worker 配置整体移入 `parsePdf()` 的动态导入之后。修复后 pdfjs 应拆成独立 chunk，非 PDF 场景不再下载。

### [P1] `china.json`（568 KB）硬编码绝对路径，在子路径部署下会 404

- **位置**：`D:/平台/frontend/src/components/EChart.jsx:33`
- **现象**：`fetch('/china.json')` 使用**根绝对路径**，但构建配置是 `base: './'`（相对路径）。
- **影响**：
  - **对用户**：当前由 FastAPI 挂在根路径下部署，恰好能工作。但 `base: './'` 的设计意图明确是「支持部署到任意子路径」（相对路径 + HashRouter），一旦部署到 `http://host/kaoyan/` 之类子路径，`/china.json` 就会 404 → 中国地图直接空白，且 `EChart.jsx:38` 只 `console.error`，**用户看不到任何提示**，表现为「地图区域空白」。
  - **对维护**：`base` 与资源路径策略不一致，后续换部署路径时是隐性坑。
- **证据**：
  ```jsx
  // vite.config.js:7
  base: './',
  ```
  ```jsx
  // EChart.jsx:33
  const res = await fetch('/china.json')
  ```
  `public/china.json` 实测 582,522 字节。
- **建议**：改用 `import.meta.env.BASE_URL + 'china.json'`（Vite 会按 `base` 注入正确前缀），与 `base` 配置保持一致；同时给地图加载失败补一个用户可见的降级提示。

### [P1] 全站无可用 lint / typecheck 脚本，共享 Form 组件的 label 未关联控件

- **位置**：`D:/平台/frontend/package.json:6-11`；`D:/平台/frontend/src/components/Form.jsx:162-168`
- **现象**：两个问题合并成条，因为它们是同一件事的两面——**没有任何自动化能拦住低级缺陷**。

  **(a) 脚本缺失**：`scripts` 只有 `dev` / `build` / `preview` / `test`，**无 `lint`、无 `typecheck`**。虽然装了 `typescript`，但 `tsconfig.json:18-19` 设了 `allowJs: true` + `checkJs: false`，`src` 下仅 2 个 `.ts` 文件（`types/index.ts`、`vite-env.d.ts`），且 `types/index.ts`（262 行类型定义）**未被任何代码引用**。实测 `npx tsc --noEmit` 输出为空，等于**什么都没检查**。

- **影响**：
  - **对用户**：读屏软件无法把标签和输入框关联，读出「表单控件，无标签」。这是**全站复用组件** `Form.jsx` 的缺陷，会扩散到所有使用该组件的表单；`AiServiceManager.jsx`、`Documents.jsx` 等虽为 label 包裹 input（隐式关联，可用），但模式不统一。
  - **对维护**：无 lint 意味着未使用变量、 Hook 依赖缺失、误用 `==` 等问题只能靠人眼发现；装了 typescript 却没启用，给人「有类型保障」的错觉，实际 `strict: true` 完全没生效。
