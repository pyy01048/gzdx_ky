# 35-MinerU 本地化实测报告（2026-10-21）

> 目标：让 MinerU 在本机**完全离线**跑通，为 PDF 侧公式/版面解析铺路
> 结论：**模型与配置已全部就绪，pipeline 可运行；但 CPU 推理在 MFR 阶段存在卡死，批量解析需 GPU**

---

## 1. 一句话结论

MinerU 的**环境、模型、配置三件套已经彻底落地且可离线运行**（`MINERU_MODEL_SOURCE=local`），
Layout 检测与公式检测实测正常；但 `.venv-ocr` 装的是 **CPU 版 torch**，
MFR（公式识别）阶段在第 16/28 张上卡死超过 2 分钟 —— 与 docx 侧发现的
「极扁公式图推理极慢」同源。**PDF 批量解析必须先解决算力（GPU torch 或 ONNX 4.x 后端）。**

## 4. 模型已完整落地（约 4GB）

位置：**`D:\平台\models\pdf-extract-kit`**（真实文件，非 HF 符号链接）

### 为什么不用 HF 默认缓存

`snapshot_download()` 在 Windows 上**创建符号链接失败**（需要开发者模式或管理员权限），
结果是 `snapshots/<rev>/` 下**全是空目录**，而 `blobs/` 里躺着 6.0GB 数据。
MinerU 按 snapshot 路径去找文件，就会报
`FileNotFoundError: ...yolo_v8_ft.pt`。

**解法**：用 `local_dir` 参数把文件**实际复制**出来：

```python
snapshot_download(
    "opendatalab/PDF-Extract-Kit-1.0",
    repo_type="model",
    allow_patterns=[...],
    local_dir=r"D:\平台\models\pdf-extract-kit",
    local_dir_use_symlinks=False,
)
```

### 已落地的关键文件

| 用途 | 路径 | 体积 |
|---|---|---|
| 版面检测（MFD） | `models/MFD/YOLO/yolo_v8_ft.pt` | 334 MB |
| 版面分析 | `models/Layout/YOLO/doclayout_yolo_docstructbench_imgsz1280_2501.pt` | 38 MB |
| **公式识别（MFR）** | `models/MFR/unimernet_hf_small_2503/model.safetensors` | **772 MB** |
| 中文 OCR | `models/OCR/paddleocr_torch/ch_PP-OCRv5_det_infer.pth` + `ch_PP-OCRv5_rec_infer.pth` | 14 + 25 MB |
| 阅读顺序 | `models/ReadingOrder/layout_reader` | — |
| 表格识别 | `models/TabRec/SlanetPlus/slanet-plus.onnx`、`UnetStructure/unet.onnx` | — |
| 表格分类 | `models/TabCls/paddle_table_cls/PP-LCNet_x1_0_table_cls.onnx` | — |

OCR 目录共 **25 个文件**（含全部语种 rec 模型）。

### MFR 模型选哪个

`mineru/utils/enum_class.py::ModelPath` 定义了两个公式模型：

- `unimernet_small = "models/MFR/unimernet_hf_small_2503"` ← **pipeline 默认用这个**
- `pp_formulanet_plus_m = "models/MFR/pp_formulanet_plus_m"`

只下 `unimernet_tiny` 是不够的，MinerU 会报
`Repo id must be in the form 'repo_name'` —— 它把本地路径当 HF repo id 传给
`transformers.from_pretrained`，说明**目标目录不存在**。

## 5. 配置：完全离线运行

`C:\Users\33884\mineru.json`（**改前已备份为 `mineru.json.bak.<ts>`**）：

```json
{
    "latex-delimiter-config": {
        "display": { "left": "$$", "right": "$$" },
        "inline":  { "left": "$",  "right": "$"  }
    },
    "models-dir": {
        "pipeline": "D:/平台/models/pdf-extract-kit",
        "vlm": ""
    },
    "model-source": "local",
    "config_version": "1.3.2"
}
```

运行时**还要**设环境变量（`mineru.json` 的 `model-source` 字段不一定会被读）：

```powershell
$env:MINERU_MODEL_SOURCE = "local"
```

原理见 `mineru/utils/models_download_utils.py::auto_download_and_get_model_root_path`：

```python
model_source = os.getenv('MINERU_MODEL_SOURCE', "huggingface")
if model_source == 'local':
    root_path = get_local_models_dir().get(repo_mode)   # repo_mode='pipeline'
    return root_path
```

**设对之后完全不发网络请求。**

## 6. 实测结果

命令：

```powershell
cd D:\平台
$env:MINERU_MODEL_SOURCE = "local"
./.venv-ocr/Scripts/mineru.exe -p "D:\平台\knowledge_base\数学\1987年考研数学三真题及解析 .pdf" `
  -o "D:\平台\temp\mineru_probe5" -m ocr -b pipeline -l ch -d cpu -s 0 -e 0 -f True
```

实测输出（1 页，扫描版数学真题）：

| 阶段 | 耗时 | 结果 |
|---|---|---|
| DocAnalysis 初始化（加载全部模型） | **20.0 s** | 成功 |
| Layout Predict | **9.6 s** | 成功 |
| MFD Predict（公式区域检测） | **7.4 s** | 成功，检出 **28 个公式区域** |
| MFR Predict（公式识别） | — | **卡在第 16/28 张，> 2 分钟无进展** |

### 关键判断

1. **模型与配置都对了** —— 能走到 MFR 并识别出 28 个公式框，证明 Layout/MFD 链路完整。
2. **MFR 卡死是算力问题，不是配置问题**：
   - 同一批模型在 **docx 公式图**上单张 0.2–0.3 s；
   - 但**极扁的图**（宽高比 > 12，如 240×15 的单行下标）单张要 **21.8 s**，
     且模型会吐残缺序列；
   - PDF 页面里这种极扁公式很多，MFR 逐张过就会卡住。
3. **`-s 0 -e 0` 只跑 1 页**，已卡住；说明**不适合在 CPU 上批量跑**。

## 7. 两个 MinerU 自身的 bug（会踩到）

### 7.1 输出子目录不自动创建

报错：

```
FileNotFoundError: [WinError 3] 系统找不到指定的路径。:
  'D:/平台/temp/mineru_probe5\1987年考研数学三真题及解析 \ocr'
```

MinerU 直接写 `-o` 下的 `<PDF名>/ocr`，**不建目录**。

**绕过**：跑之前手动建：

```powershell
mkdir "temp/mineru_probe5/1987年考研数学三真题及解析 /ocr"
```

注意 PDF 文件名本身带**尾随空格**（`...解析 .pdf`），目录名也会带，别手抖去掉。

### 7.2 空格与中文路径

`-o` 路径里的中文和空格本身没问题（实测能走到 MFR），
但配合 7.1 的缺目录 bug 会放大报错噪音。

## 8. 下一步（按性价比排序）

1. **优先：给 MinerU 换 GPU 算力**
   - 选项 A：在 `.venv-ocr` 里重装 CUDA 版 torch（`pip install torch --index-url https://download.pytorch.org/whl/cu128`），
     约 2.5GB 下载；之后 `-d cuda`，预计 MFR 从「卡死」变「0.1–0.3 s/张」。
   - 选项 B：改用 MinerU **4.x 的 ONNX 后端**（模型已在 `~/.mineru/models/MinerU-4_models_onnx`，
     819MB，含 `PP-FormulaNet_plus-M.onnx`）——ONNX Runtime 可走
     `CUDAExecutionProvider`，且 `backend-main-fastapi/.venv` 里的 onnxruntime 已装好。
     **推荐 B**：不重下 torch，且本项目已有一套可用的 ONNX 公式识别实现
     （`services/formula_latex.py`，34+ 测试绿，真实公式图 11/12 成功）。
2. **PDF 侧批量解析**：仅在 GPU 就绪后做，且先抽 20–30 份代表样本测 CER，
   不要全量 3129 个 PDF 一把梭。
3. **docx 侧已经在跑**：`scripts/backfill_docx_formulas.py` 走
   `services/formula_latex.py`（PP-FormulaNet ONNX），不依赖 MinerU。
