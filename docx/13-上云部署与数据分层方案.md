## 2. 问题一：数据库放百度网盘能方便使用吗？

### 2.1 直接答案：分用途，两种答案

```
作为在线数据库（多人/多端实时读写）  →  ❌ 绝对不行，会损坏数据
作为离线备份 / 大文件分发            →  ✅ 非常合适，推荐做
```

### 2.2 为什么不能当在线数据库（技术根因）

**根因 1：SQLite 强依赖文件系统语义，网盘给不了**

SQLite 的 ACID 建立在两个假设上：
1. **文件锁是可靠的**（WAL 模式通过 `-shm` 共享内存做多进程协调）
2. **fsync 的落盘顺序是有保证的**

网盘同步盘（百度网盘客户端 / 任何网盘同步机制）两条都不满足：
- 同步是**异步最终一致**的：`kaoyan.db` 改了，`kaoyan.db-wal` 还没传完，另一台机器读到的就是半个状态
- `-shm` / `-wal` 两个辅助文件同步顺序无法保证
- 结果不是"慢"，是 **`database disk image is malformed`**，直接损坏

> 你的库现在是 **WAL 模式**且当前就有 444KB 未合并的 `-wal` 文件，这是最容易出事的状态。

**根因 2：百度网盘 API 的物理限制（官方硬性约束）**

| 限制 | 数值 | 影响 |
|---|---|---|
| 单用户 API 频率 | **20 次/秒** | 一次页面加载若涉及多次 IO 就会被限流 |
| 下载链接 dlink 有效期 | **8 小时** | 需持续刷新，不能当持久地址 |
| 浏览器直接下载上限 | **50 MB** | 你的库 294MB，网页端根本下不了 |
| 第三方应用可用目录 | **只能 `/apps/<应用名>/` 一个 folder** | 无法组织多目录结构 |
| OAuth token | 需定期 refresh | 服务化运维成本高 |

**根因 3：同步冲突会产生 `xxx(1).db` 副本**
两端同时写 → 网盘判定冲突 → 生成副本 → 你永远不知道哪个是最新的。

### 2.3 百度网盘正确的三种用法（推荐）

#### 用法 A：每日冷备份归档 ✅ 强烈推荐

这是网盘唯一的正确打开方式，而且**正好解决你诊断里 5GB 磁盘堆积的问题**。

```python
# tools/backup/backup_to_netdisk.py
"""每日真库备份 → 打包 → 上传百度网盘 /apps/kaoyan-platform/backups/
关键：必须用 sqlite backup API，不能 cp（会丢未合并的 WAL 数据）
"""
import sqlite3, zipfile, os, time, subprocess
from datetime import datetime

DB = r"D:\平台\database\kaoyan.db"
OUT_DIR = r"D:\平台\exports\backup"
KEEP_LOCAL = 3          # 本地只留最近 3 份
KEEP_REMOTE_DAYS = 30   # 网盘保留 30 天


def safe_snapshot(dst: str):
    """WAL 安全的快照：走 SQLite Online Backup API"""
    src = sqlite3.connect(f"file:{DB}?mode=ro", uri=True)
    out = sqlite3.connect(dst)
    with out:
        src.backup(out)          # ← 关键：不是 shutil.copy
    src.close(); out.close()


def main():
    ts = datetime.now().strftime("%Y%m%d_%H%M%S")
    tmp_db = os.path.join(OUT_DIR, f"kaoyan_{ts}.db")
    os.makedirs(OUT_DIR, exist_ok=True)

    safe_snapshot(tmp_db)                      # 1. 一致性快照

    zip_path = tmp_db + ".zip"
    with zipfile.ZipFile(zip_path, "w", zipfile.ZIP_DEFLATED, compresslevel=6) as z:
        z.write(tmp_db, arcname=f"kaoyan_{ts}.db")
    os.remove(tmp_db)

    # 2. 上传（用百度网盘开放平台 API，需 OAuth access_token）
    #    path 必须在 /apps/<应用名>/ 下
    subprocess.run([
        "python", r"D:\平台\tools\backup\pan_upload.py",
        zip_path, f"/apps/kaoyan-platform/backups/kaoyan_{ts}.zip"
    ], check=True)

    # 3. 本地只留 3 份，解决 5GB 堆积
    zips = sorted((f for f in os.listdir(OUT_DIR) if f.endswith(".zip")), reverse=True)
    for old in zips[KEEP_LOCAL:]:
        os.remove(os.path.join(OUT_DIR, old))
    print(f"[OK] {ts} 本地占用已收敛，剩余 {min(len(zips), KEEP_LOCAL)} 份")


if __name__ == "__main__":
    main()
```

**收益**：`database/` 目录从 5.0GB → 稳定在 ~900MB，且备份异地容灾。

#### 用法 B：76GB 学习资料的按需分发源 ✅

这招很关键：**服务器上一份 PDF 都不存**，用户点"下载真题"时由后端生成一个临时 dlink 让他直接从网盘下，流量不经过你的服务器。

- 服务器磁盘压力：0
- 带宽压力：0（3M 小水管也扛得住）
- 注意：dlink 有效期 8 小时，每次都要重新取

#### 用法 C：大模型的异地归档

5.8GB LoRA + 3.1GB reranker + 678MB checkpoints → 全扔网盘，本机腾出 9.6GB。要用再拉。

## 3. 问题二：本地模型能不能放别的地方存储？

**答案：能，而且必须分层。核心判断标准是「这个模型在线上要不要被调用」。**

### 3.1 分层存储策略

| 模型 | 体积 | 线上是否必需 | 存放位置 |
|---|---|---|---|
| **bge-small-zh-v1.5**（embedding） | 91 MB | ✅ **必需**，检索链路每一步都要 | **服务器本地磁盘** |
| Qwen2.5-1.5B merged | 5.8 GB | ❌ 不需要 | 百度网盘归档 / 本地保留 |
| LoRA checkpoints | 678 MB | ❌ 不需要 | 百度网盘归档 |
| bge-reranker | 3.1 GB | ❌ 不需要（可后置） | 百度网盘归档 |

**为什么 embedding 必须留在服务器上？**
你的检索是 `FTS5 BM25 + 向量 KNN + RRF 融合`（`services/search_service.py`）。如果向量要走 API，27,893 个分块每次查询都要联网编码，**延迟从毫秒级变成秒级**，而且按量付费。91MB 的模型加载进内存也就 ~400MB RSS，2C4G 完全扛得住，CPU 推理单条几十毫秒。

### 3.2 模型文件外置的正确姿势（本机也要做）

如果你暂时不上云，只想本机瘦身，用**符号链接**把大文件挪到别的盘：

```bat
:: 以管理员身份运行，把 5.8G 的 merged 模型挪到 D:\models
mkdir D:\models
move "D:\平台\backend-main-fastapi\data\lora_finetune\merged" "D:\models\qwen25-1.5b-merged"
mklink /D "D:\平台\backend-main-fastapi\data\lora_finetune\merged" "D:\models\qwen25-1.5b-merged"
```

> ⚠️ Windows 符号链接需要管理员权限；路径务必用英文，中文路径会让 transformers 在某些版本上报编码错误。
> ⚠️ 挪动前先确认代码里的加载路径是配置化的（环境变量优先），否则硬编码会失效。

### 3.3 服务器上的 AI 分工建议

```
┌─ 服务器端 ─────────────────┐        ┌─ 本地/你的机器 ──────────┐
│ bge-small-zh (91MB)  ✅必留  │        │ Qwen2.5-1.5B LoRA  5.8G  │
│ FTS5 + sqlite-vec    检索    │        │ bge-reranker       3.1G   │
│ LLM 生成 → 在线 API   按量付费│        │ 训练/微调环境             │
└─────────────────────────────┘        └──────────────────────────┘
                 ↓
         用户拿到同样的体验，服务器只需 1GB 内存跑 AI
```

你已经有 `ai_providers` 表（13 条配置）和双引擎路由，改造成本很低：**服务端把本地 LLM 分支关掉，只保留 API 分支**即可。

## 4. 问题三：100 元预算，怎么做成公开站？

### 4.1 ⚠️ 先说三个前置障碍（不解决不能公开）

这三条是实测出来的，比钱更致命：

#### 障碍 1：**你的系统现在没有用户表**

```
✅ 实测：models.py 中不存在 User / Account 模型类，59 张表里也没有 users 表
```

当前是**单机单人设计**。直接放到公网意味着：
- 任何人都能改任何数据
- 没有数据隔离，A 用户的错题本 B 用户能看到

**这是公开的硬前置**，工作量约 3-5 天（用户表 + JWT + 各业务表加 owner_id + 所有查询加过滤）。

#### 障碍 2：SQLite 的写并发上限

SQLite WAL 是**多读单写**。单人刷题没问题，公开后多人同时提交答案会遇到 `database is locked`。

**务实建议：先不要迁 PostgreSQL。** 理由：
- 你的代码对 SQLite 私有特性**重度依赖**（17+ 处 FTS5、sqlite-vec、jieba 分词写入、BM25、RRF 融合）
- 迁 PG 要处理**中文分词**（PG 原生 tsvector 不切中文，需装 zhparser/pg_jieba/pgroonga）
- 你的场景是**低频写**（答题、埋点），不是高并发交易

**过渡手段**（成本几乎为零）：
```python
# database.py 的 engine 配置里加
connect_args={"check_same_thread": False, "timeout": 30}
# 启动时执行
PRAGMA journal_mode=WAL;
PRAGMA busy_timeout=30000;     # 写锁等待 30 秒而不是立刻报错
PRAGMA synchronous=NORMAL;
```
配合连接池串行化写，撑几十人同时在线刷题绰绰有余。**真到了几百人再迁 PG，那时候你已经有用户了，值得投入。**

#### 障碍 3：备案

国内服务器 + 域名 → **必须 ICP 备案**，免费但耗时 7-20 天。
不想等：用 `IP:端口` 访问（不体面），或选中国香港/海外节点（延迟 +50~100ms）。

3. 有余力把静态资源丢到对象存储 + CDN（腾讯云 COS 50GB 存储约 10 元/月）

### 4.7 部署步骤（精简版）

```bash
# 1. 服务器初始化（Ubuntu 22.04）
apt update && apt install -y python3.11 python3-pip nginx git

# 2. 只传必要文件（别传 node_modules / knowledge_base / data）

      --exclude='*/data/lora_finetune' --exclude='*/data/storage' \
      ./ user@server:/opt/kaoyan/

# 3. 构建前端
cd frontend && npm ci && npm run build && cd ..

# 4. systemd 托管后端
cat > /etc/systemd/system/kaoyan.service << 'EOF'
[Unit]
Description=Kaoyan Platform API
After=network.target

[Service]
WorkingDirectory=/opt/kaoyan/backend-main-fastapi
Environment="DATABASE_PATH=/opt/kaoyan/database/kaoyan.db"
ExecStart=/usr/bin/python3 -m uvicorn main:app --host 127.0.0.1 --port 8000 --workers 1
Restart=always

[Install]
WantedBy=multi-user.target
EOF
systemctl enable --now kaoyan

# 5. Nginx 反代
cat > /etc/nginx/sites-available/kaoyan << 'EOF'
server {
    listen 80;
    location / {
        root /opt/kaoyan/frontend/dist;
        try_files $uri $uri/ /index.html;   # SPA 路由兜底
        gzip on;
        gzip_types text/css application/javascript application/json;
    }
    location /api/ {
        proxy_pass http://127.0.0.1:8000/;
        proxy_read_timeout 300s;            # AI 接口有 300s 超时设计
    }
}
EOF
ln -s /etc/nginx/sites-available/kaoyan /etc/nginx/sites-enabled/
nginx -t && systemctl reload nginx

# 6. HTTPS（certbot 免费证书）
certbot --nginx -d your.domain.com

# 7. 每日备份定时任务
echo "0 3 * * * /usr/bin/python3 /opt/kaoyan/tools/backup/backup_to_netdisk.py" | crontab -
```

### 4.8 常见坑（务必先看）

| 坑 | 后果 | 解法 |
|---|---|---|
| **Windows 开发 → Linux 部署的路径大小写** | `Kaoyan.db` vs `kaoyan.db` 在 Linux 上是两个文件 | 全部改小写，代码里用 `os.path.join` |
| **中文路径 + 中文文件名** | transformers / jieba 加载失败 | 路径全英文，文件名另行 user-facing |
| **`--workers > 1`** | SQLite 多进程写直接锁死 | uvicorn 必须 `--workers 1` |
| **未合并的 WAL** | `cp` 备份丢数据 | 一律用 sqlite backup API（你的项目已经踩过一次了） |
| **宝塔面板默认装 MySQL 占内存** | 2C4G 直接被吃掉一半 | 别装面板，纯命令行为佳，或不装 MySQL |
| **3M 带宽下前端 bundle 2MB+** | 首屏 10 秒+ | 分包 + gzip，详见 4.4 |
| **公开后被刷 LoRA/AI 接口** | 账单爆炸 | AI 端点加频率限制 + 每日预算上限 |
| **爬虫端点暴露** | 采集 IP 被封，甚至法律风险 | 加管理员鉴权，公开版本最好直接摘掉采集功能 |

---

## 5. 我建议的执行顺序

```
第 1 步（本周，0 成本）
   └─ 先别急着买服务器。把备份脚本搭起来（第 2.3 节），
      database 目录从 5GB 降到 1GB 以内，顺手验证 WAL 安全快照能跑通

第 2 步（1-2 周）
   └─ 补用户表 + JWT。这是公开的唯一硬前置，逃不掉，早做早省事
      顺手把 owner_id 加到涉及私有数据的表上

第 3 步（花 89 元）
   └─ 买火山引擎 2C4G 档，先部署一个「只读版」（不含 AI 生成）
      验证：能不能访问、检索快不快、有没有人大规模愿意用

第 4 步（看第 3 步反馈）
   └─ 有人用 → 开 AI、买域名、备案、加固采集端点
      没人用 → 你已经花掉的只有 89 元和一个周末
```

> **最坏情况的成本：89 元。** 这比先花两周做用户体系结果发现没人用，要划算得多。

## 6. 附：本方案的可复用事实

- 必须上云资产总量：**≈600MB**（代码 50MB + 真库 294MB + embedding 91MB）
- 无需上云：**104GB**（76GB 原始资料 + 12GB 文档副本 + 9.6GB 模型）
- embedding 模型：`Qdrant/bge-small-zh-v1.5`，91MB，CPU 推理可用
- 检索链路：`FTS5 BM25 + 向量 KNN + RRF 融合`（`services/search_service.py`），迁移 PG 有大坑
- 无 User 表、无鉴权 → 公开的硬前置
- uvicorn 必须 `--workers 1`（SQLite 单写）
- 备份必须 `sqlite3 backup API`，禁用 `cp`
