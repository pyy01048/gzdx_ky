## 二、对既有文档方向的裁定（矛盾点逐条裁决）

外部草案（chunk 级三层标签 + 三路融合 + 文档聚合）与 docx 已有规划存在交叉，裁定如下：

### 2.1 「三路融合」中的 LoRA 小分类模型 —— **本阶段不做**
草案提议用 RoBERTa 底座 + 自有数据 LoRA 微调一个学科分类器。裁定**不做**：
- 显存现实：本机 8GB 单卡已被答疑模型 + 抽取模型占用（`kp_extract` 并发注释明确"8GB 单卡别调高"）；
- 数据现实：几百条标注训多科细分类（taxonomy 全集远超 8 科）不稳定，且标注本身要先建；
- **替代**：草案的"路径2"由**现有关键词打分**（`kb_service` 词表，零成本、可解释）承担；"路径3 LLM 兜底"复用 `kp_extract._chat_local` 的本地 Ollama 同步调用范式。只有当第五节的评估闭环证明向量+关键词两路 F1 仍不达标时，才回头补小分类模型——**用数据决定，不用直觉决定**。

### 2.2 学科枚举 —— **以 taxonomy 为唯一事实源，拒绝草案的 8 科表**
草案的 8 科（高数/信号与系统/光电信息…）与仓库不一致。唯一事实源：
- `services/taxonomy.CORE_SUBJECTS`（6 细分科）+ MAJOR/EXT；
- `services/doc_lock_subjects.DOC_LOCK_ALLOWLIST`（文档归属叶子科）；
- 保留 `kp_extract._FLATTENED_LABELS` 压平黑名单（"数模电/公共课"等合并标签绝不落库，11 号文档 0854 三层学科模型的教训已吸收）。

### 2.3 文档级聚合 ≠ 抛弃文档级标签
`Document.subject` 与文档学科锁机制保留（408 教材不能被 chunk 投票成"数据结构"）。chunk 标签解决的是**文档内部混合内容**的检索/路由精度；聚合只回写"原标签为空/其他/低置信"的文档。

### 2.4 答疑微调模型选型：3B vs 1.5B 之争 —— **用 eval_qa_model 裁决**
00 号文档称 Qwen2.5-**3B**+LoRA，12 号实测为本地 Qwen2.5-**1.5B**。两说并存且都没量化过收益。裁定：**先建评测，再谈选型**。`eval_qa_model.py` 跑"基座 vs 合并 LoRA vs 云端参照"三列对比，客观题判分为主、LLM judge 为辅；若 1.5B 微调在学科切片上无显著增益（<3pt），停止本地微调线，资源转投检索质量（07 号方向三仍成立）。

### 2.5 评估体系三套并存（RAGAS / open-rag-eval 指标 / answer_confidence）—— **按对象拆分，不再互斥**
- **检索质量**：沿用 `retrieval_eval.py` recall@k ✅；
- **生成质量（答疑）**：`eval_qa_model.py`（本方案新增）客观题判分 + 拒答率 + 抽样 LLM judge；RAGAS 全量指标**不引入**（依赖重、与本地 Ollama 链摩擦大），只借它的 faithfulness 思想做幻觉抽检；
- **运行时置信**：`answer_confidence_schema` / `retrieval_gate` 保持在线门控角色 ✅。
三者分别覆盖"离线回归—模型对比—在线兜底"，互不替代。

### 2.6 草案中"实体消重/布局感知解析"—— **吸收但后置**（见第七节阶段 C/D）
仓库已有 `ocr_layout.py`（带坐标版面切题 ✅）和 `smart_chunk_text`（章节标题优先 ✅），布局解析不是从零；知识点向量消重吸收草案思路，排在打标与评测闭环之后——**先证明分类可用，再让图谱变大**，避免 10 号文档警告的"图谱爆炸"。

### 2.7 FSRS/BKT/掌握度热力图 —— **维持 10/12 的裁定：事件埋点是硬前置**
`study_events` 0 行、`answer_records` 仅 18 行 ✅。本方案不做排期，只要求：题库/答疑产物继续带 `knowledge_node` 关联，数据回流后这些方向即可启动（与 08-深度开发计划 M 系列一致）。

## 三、定型架构：chunk 级三路融合打标 + 文档聚合

```
上传/重解析 → ingest_text 切块（现有）
  → 【chunk_classifier】三路并行评分
      路1 学科原型质心：bge 真模型 embedding × 各科质心余弦相似度   （新）
      路2 关键词计分：  kb_service.classify_subject_confidence     （复用）
      路3 LLM 判定：    仅低置信/两路分歧时触发，一次输出 l1/l2/l3+置信度 （复用 Ollama 范式）
  → 加权融合（默认 0.45/0.45/0.10，LLM 缺席时 0.5/0.5）→ 写 chunk 三层标签 + confidence + source 留痕
  → 文档聚合：多数 chunk 学科 →（仅当原学科缺失/低置信）回写 Document.subject；少数派 chunk 保留独立标签
  → 任务路由：l3_content_type 决定 知识点抽取 / 题库抽取 / 公式入库
```

要点（与草案的差异已在第二节裁定）：
1. **最小单元是 chunk，标签存 chunk**，文档标签只是聚合视图——多学科混合文档由此可解；
2. **原型质心只用 bge 真向量**：`embedding_service.is_local_model_available()` 不可用时整路降级、权重重分配并在 `classify_source` 留痕 `no_bge`；**绝不拿 `knowledge_chunks_vec` 里已存向量凑数**（512 维混口径，见第一节问题 6）；
3. **成本闸门**：LLM 路只吃融合低置信样本（阈值默认 0.75，env 可调），全局信号量沿用 `SMART_INGEST_KP_MODEL_SLOTS` 机制，不打爆 Ollama；
4. **任务路由落地形态**：L3=习题/例题 → 喂 `document_analyzer.extract_questions`/`qbank_builder`；L3=定义/定理/理论 → 喂 `kp_extract`；L3=公式 → `formula_service`。存量抽取脚本不改协议，只加"按 L3 过滤输入"一步。

## 四、数据模型变更

```sql
-- knowledge_chunks 加列（SQLite 在线 ALTER，沿用 V4.0 补列惯例）
l2_chapter        VARCHAR(200)   -- L2 章节/模块，如"连续时间系统的时域分析"
l3_content_type   VARCHAR(30)    -- 定义|定理|理论陈述|例题|习题|证明|公式|实验步骤|其他
classify_confidence FLOAT        -- 融合置信度 0~1
classify_source   VARCHAR(30)    -- vector|keyword|fusion|llm|no_bge|fallback（留痕，口径对齐 kp_extract.subject_source）

-- 新表 subject_prototypes：学科原型质心
subject TEXT, dim INT, vector BLOB, n_samples INT, engine TEXT('bge'), built_at DATETIME
-- PRIMARY KEY(subject, engine)  -- engine 维度锁死，杜绝混口径

-- 新表 annotation_sample：评估闭环标注集（人工修正回流）
chunk_id INT, label_l1 TEXT, label_l3 TEXT, annotate_user TEXT, source TEXT('manual_fix|eval_seed'), created_at DATETIME
```

`Document.subject_source` 现有口径（ima/空）不动，文档聚合留痕写 `Document.subject` 旁的日志字段即可，不再挤占。

## 五、评估闭环（先于任何词表/权重调优）

1. `scripts/build_subject_prototypes.py`：按**现有高置信标签**分层抽样 chunk（每科 ≥40 块，排除 `is_parse_failure`、OCR 碎片、`其他/真题综合`），bge 编码后求质心入库；
2. **标注集**：随机抽 200~300 chunk（刻意过采样易混对：数学↔信号与系统、数电↔模电、物理↔数学），人工标注 L1/L3，存 `annotation_sample`；
3. `scripts/chunk_classify_eval.py`：输出整体 + 分科 accuracy / macro-F1、低置信占比、三路一致率——**所有权重/阈值改动必须过这份报表**；
4. 前端/接口提供 chunk 标签人工修正入口，修正样本自动进 `annotation_sample(source=manual_fix)`，滚动扩充标注集；
5. 若两路融合在标注集上 F1 < 0.85，才触发第二节 2.1 预留的小分类模型议题。

## 六、答疑模型评测与训练回流

`backend-main-fastapi/scripts/eval_qa_model.py`：
- **题源**：`QuizQuestion` 客观题按 `subject × q_type` 分层抽样（默认 300 题），题干+选项组 prompt，system 带学科；
- **被测**：`--models qwen2.5:1.5b-instruct,kaoyan-assistant,...` 多列同跑，走本地 Ollama（沿用 `_build_opener` 绕代理的实测教训）；支持 `--with-rag` 开关对照"裸模型 vs RAG 增强"，把模型问题与检索问题分开归因；
- **判分**：正则抽选项判对错；`--judge` 可选 LLM 复核主观题/判"实质等价正确"；统计 accuracy、拒答/超短答率、按学科切片；
- **产出**：JSON + Markdown 对照表，写入 `exports/`；**3B vs 1.5B、要不要继续本地微调，以这份表为准**（裁定 2.4）；
- **回流**：答疑点踩/人工修正的答案对写入 `SFTExample`（表已存在 ✅），`build_qa_dataset.py` 增加 split 防泄漏（chunk 同源题不得同时进 train/eval）。

## 八、风险与避坑

1. **混口径向量**：原型库与 chunk 编码必须同一引擎同一模型版本，表上 `engine` 主键位已锁；将来换模型走"重建+切版本"而非原地覆盖。
2. **LLM 打标幻觉**：L2 章节名模型易编造——约束"优先从块内标题/文档目录候选中选取，无依据则留空"；L1 非法值走 `_model_subject` 同款黑名单校验。
3. **算力**：3.4 万存量 chunk 回填按批跑，路1/路2 纯本地毫秒级，LLM 预算 = 低置信比例 × 单块调用，先抽样估算再全量。
4. **OCR 噪声块**：`text_is_mojibake`、拉丁比例等既有门禁先过滤，噪声块只标 `其他` 不进标注集分母。
5. **别把打标变成第二个"伪完成"**：本方案每阶段验收都要求真库数字（报表/覆盖率），不是"代码合入即 ✅"——这是 12 号诊断对四条伪完成流的直接教训。

### 9.2 学科池扩容（域外语料的根因修复）✅

原判读：**问题不是域内错标，而是候选集不完整**——chunk 级三路融合在结构上不可能发现"库里出现了新的一门统考学科"。

- `services/taxonomy.py` 增 `CROSS_SUBJECTS` 7 科（管理类联考综合、经济类联考综合、法律硕士专业基础、教育学专业基础、心理学专业基础、西医综合、中医综合），`ALL_SUBJECTS` 共 35 科；别名一律用复合键（`312心理学` 而非 `312`），因为归一匹配是 `std in s` 的子串语义。
- `services/doc_lock_subjects.py` 的 `DOC_LOCK_ALLOWLIST` 同步纳入这 7 科。
- 文档级判定 `scripts/label_doc_discipline.py`：文件名里的考试代码/学科名＝强证据（`NAME_WEIGHT=25.0`，实测正文术语密度最高能虚高到 14.6，所以密度只能当佐证），**只有密度证据的判定一律拒绝**（`skip_density_only`），名称命中且唯一命中才无视 margin 放行；正文 blob < 1000 字不参与。
- 结果：**231 篇文档重判落库**，7 个新学科的 bge 质心重建（每科 ≥10 种子）；回滚数据在 `temp/discipline_audit_1012*.json` 的 `current` 字段，DB 备份 `database/kaoyan.db.bak-1012-before-cross-subject`。

### 9.4 两条否决（实测，别再重试）✅

- **乱码/重复弃权门控**：全库命中 18%（仅数学就 4664 块），样本上域内 recall 0.947→0.842，代价远大于收益。
- **低置信广播到所有学科池**：precision 0.755→0.302，直接把学科池打穿。

### 9.5 择校可靠度（P3）✅

### 9.9 第二志愿放行「落地检索侧」——**实测否决**（`eval_runs` #11）✅

§10 曾把「第二志愿放行」记成"零精度代价把域内 recall 0.930→0.965"，因此被列为下一步收益项。本轮要落地时发现该结论**来自评测脚本的口径缺陷**，不是数据事实：

- `recognition_policy_eval.py::score()` 里，`use_alt` 只放宽了 **recall** 的判定（`visible = sub==gold or alt==gold`），而 precision 与域外污染的分母仍按 **top-1 组池**（`in_scopes = sub in SCOPES`）。生产检索是 `subject = S OR alt_subject = S`，alt 命中的块同样进池，分母必须一起放宽。
- 按生产语义重算（同一 147 样本、同一打分，junk=macro）：

| 口径 | precision | 域内 recall | F1 | 域外污染 | 学科池曝光 |
|---|---|---|---|---|---|
| 仅 top-1（现网） | 0.883 | 0.930 | 0.906 | 27.3% | 120 |
| top-1 **或** alt（生产放宽） | **0.683** | 0.965 | **0.800** | **30.3%** | 161 |

  Δrecall +3.51pt，但 Δprecision **−20.01pt**、ΔF1 **−10.60pt**。alt 带来的 41 次新增曝光里只有 4 次判对（域内 top1 打错而 top2 对的块总共 4/114），其余全是把块塞进错误学科池。**否决，不落地。**
- 已修的是评测本身：`score()` 改为"池成员条件 = 检索放行条件"（同一块占两个池记两次曝光），`stamp()` 弃权时 **alt 一并置空**（弃权语义是"不猜"，生产里 alt 列同样不写）。回归锁 `tests/test_recognition_policy_metric.py`（6 条纯函数测试，0.15s）——其中一条专门断言"放宽放行必须同时放宽 precision 分母"，防止旧数字被重新用来立项。
- 顺带修掉一处陈旧硬编码：`[3]` 置信门控广播的否决说明原写死 `precision 0.755→0.302`（历史语料），现改为运行时计算，本轮实测 0.862→0.445，结论不变（仍是否决）。

落地 #30 时顺手做的体检，挖出一个比 #30 更值钱的真 bug：**学科过滤打在镜像列上，而镜像列是入库时的拷贝**。

也就是说：两轮全库回填 + 弃权规则改了 9704 块的学科，检索侧一条都没吃到；1380 个弃权块里 1235 个照样出现在原学科池。

修复（`services/chunk_classifier.py`）：
- 新增 `sync_mirror_subjects(db, chunk_ids=None)`，`classify_document` 在 `db.commit()` 之后按本篇块集合调用，返回值新增 `mirror_synced`；镜像表不存在时只 `logger.warning` + 回滚本次同步，**不影响已提交标签**（沿用路3 的"绝不抛"契约）。
- 写法上有一条性能红线：FTS5 的 `chunk_id` 是 UNINDEXED、rowid 自增（rowid ≠ chunk_id），逐行 `WHERE chunk_id=?` 每行都要全表扫描——实测 199 块 **3.1s**，外推全库回填 ≈ 6600s；改成单条关联子查询后**整表 0.62s、限定块集合 0.03s**（回填总开销 +1.6%）。
- 新增 `scripts/sync_chunk_mirrors.py`：`--dry-run` 体检 / 默认幂等同步 subject / `--prune-orphans` 显式删除"chunk 已不存在"的镜像行。**从不删除 chunk**，孤儿清理默认关闭。
- 现网已执行同步并复测：**漂移 15.90%→0.00%，弃权未同步 1235→0（vec 同步 7.15%→0%、232→0）**，重跑 `--dry-run` 结果一致（幂等）。`/api/ai/rag-search` 带 `subject` 冒烟正常返回。
- 回归锁 `tests/test_chunk_mirror_sync.py`（5 条，1.65s，纯临时库）：fts+vec 双镜像逐块等于 chunk 表标签、全库模式幂等、镜像表缺失返回 −1 不抛、空 id 集合不写、`classify_document` 弃权块同步成「其他」。

1. **人工修正端点绕过镜像同步（同类错误的第二个实例）**：`POST /api/documents/chunks/{chunk_id}/label` 提交 `chunk.subject` 后直接返回，从不调 `sync_mirror_subjects`——人工把块改成「模拟电子技术」，检索侧仍按旧学科过滤，正是 §9.10 刚修完的那个坑在人工路径上重演。现已接入同步，响应新增 `mirror_synced` 字段把两侧写入结果暴露给调用方。全库扫描（把 `chunk.subject` 的所有赋值点找出来）确认写入点只有两处：`chunk_classifier` 与这个端点，现已都走同步。
2. **UPDATE 语义看不见"缺失行"**：`sync_mirror_subjects` 用 `UPDATE … SET subject=(子查询)`，块若压根不在镜像里，UPDATE 一行都不动、`rowcount` 也正常返回，调用方看不出异常——于是"改了标签"实际改了个检索召不到的块（FTS 缺 59 块、vec 缺 42925 块，这不是理论风险）。现补 `SELECT DISTINCT key` 存在性核对，缺失时 `logger.warning("检索镜像 %s 缺 %d/%d 个块（chunk_ids=…），本次学科改动对检索无效；需重建该镜像索引"）`。
3. **全库模式会把孤儿镜像行的学科刷成 NULL**：关联子查询对已删 chunk 返回 NULL，孤儿行学科被抹掉后，体检脚本会把"孤儿行"误报成"学科漂移"。现两条路径统一加 `AND EXISTS (…)` 守卫，孤儿行原样保留，交 `--prune-orphans` 显式处理。

回归锁 `tests/test_chunk_mirror_sync.py` 由 5 条扩到 **8 条**（新增：缺失行必须告警、全库同步不动孤儿行、人工修正端点写通两侧镜像），全量套件实测 **466 passed / 1 skipped / 1 xfailed（66.43s）**。

**仍未解决（下一轮）**：`knowledge_chunks_vec` 只覆盖 30.17% 的块（向量召回天然只跑三分之一语料，且历史哈希向量与 bge 同为 512 维不可混用）；孤儿镜像 243/267 行待人工确认后再清；59 块未进 FTS 镜像。
