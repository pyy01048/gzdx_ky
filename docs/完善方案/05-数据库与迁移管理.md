# 05 · 数据库与迁移管理

> 覆盖问题：R07（无迁移版本账本）、R13（scorelines NULL/大表归档）、R28（表/视图双轨、无数据字典）
> 优先级：P1 ｜ 预计工作量：账本 M；NULL 治理 M；数据字典 S；归档 M

## 1. 现状与证据

### 1.1 迁移机制：编号 SQL + create_all，无版本表

- `core/sql/` 现有 **48 个编号幂等 SQL**（095_quiz_sessions、099_favorites、104_users、108_user_data_isolation、110_question_images…），靠 `scripts/execute_core_sql.py` 人工按序执行。
- `main.py` startup 同时跑 `Base.metadata.create_all(bind=engine)`（ORM 线）+ 若干"幂等补建原生表"段。
- `migrate.py` 是 SQLite 线的迁移入口；PG 线没有对应物。
- plan-gap/00 自述："**无版本表，增量靠人工按序执行**"；项目决策"有意不用 Alembic"。
- 后果实测：10-28 全线检查发现 **memory 三表 + 2 个枚举在 PG 完全不存在**（ORM 定义了但 create_all 从未成功覆盖），8 个接口必 500——这就是"多轨建表、无账本"的直接产物。服务器侧 push_update.py 还要在部署时手工插播 3 条 SQL，漏一条就是线上缺列。

### 1.2 表/视图双轨与规模

- 109 张表 vs 59 个 ORM 类；约 47 张原生表（code_*、exam_*、kaoyan_* 多数、quiz_attempts/sessions、textbook_* 等）不在 ORM。
- 视图与真实表并存：`subject_config`（视图）vs `subject_configs`（表，47 行）；`kaoyan_subjects`（视图 = disciplines）。10-28 的 P1-3 就是脚本往视图写数据失败。
- 无数据字典：109 张表的用途、归属域、写入方只能靠读代码反推。

### 1.3 大表与数据质量

- `kaoyan_scorelines` **182,748 行**，其中 **152,377 行 major_id 为 NULL**（10-28 回填 12,452 行后剩余；源数据多来源重复导致无法安全关联）。README 已知短板自述"分数线表无上限，采集中持续增长，需要归档策略"。
- 备份体系存在（backup_service / backup.sh / 各修复报告附备份表），但**无恢复演练记录**——备份没验证过恢复 = 薛定谔的备份。

## 2. 完善标准

1. **单一迁移账本**：`schema_migrations` 表记录每个已执行脚本（编号、名称、checksum、执行时间、耗时）；启动/部署时自动补跑未执行项，**任何环境可从零重建到当前 schema**。
2. create_all 与 SQL 脚本的边界明确：create_all 只负责"全新库兜底"，**结构变更一律走编号 SQL**；两者一致性有测试守卫。
3. 视图只读：ORM 不得映射可写视图；写入一律指向真实表（P1-3 类问题有 AST/测试守卫）。
4. scorelines：NULL 率从 83% 降到 <20%（专业名归一化二次回填），剩余进归档表；主表有年度归档策略与行数上限告警。
5. 数据字典自动生成（表/列/注释/行数/归属域/写入方），随 CI 刷新。
6. 每季度一次恢复演练：最新加密备份 → 恢复到临时库 → 行数/关键表校验 → 记录报告。

## 3. 落地步骤

### 3.1 schema_migrations 账本（尊重"不用 Alembic"决策，补最小账本）

`core/sql/000_schema_migrations.sql`：
```sql
CREATE TABLE IF NOT EXISTS schema_migrations (
    version     TEXT PRIMARY KEY,          -- '108_user_data_isolation'
    checksum    TEXT NOT NULL,             -- 脚本文件 SHA256，防"执行后被偷改"
    applied_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    duration_ms INTEGER,
    applied_by  TEXT                       -- 'startup' / 'push_update' / 手工执行人
);
```

改造 `scripts/execute_core_sql.py` 为账本感知运行器（核心逻辑）：
```python
def run_pending(conn, sql_dir: Path, applied_by: str) -> list[str]:
    files = sorted(sql_dir.glob("[0-9]*.sql"))          # 编号序
    done = {r[0]: r[1] for r in conn.execute(
        "SELECT version, checksum FROM schema_migrations")}
    executed = []
    for f in files:
        ver = f.stem
        digest = hashlib.sha256(f.read_bytes()).hexdigest()
        if ver in done:
            if done[ver] != digest:
                raise SystemExit(f"[中止] {ver} 已执行但文件被修改（checksum 不符）；"
                                 f"结构变更请新增编号脚本，禁止改历史脚本")
            continue
        t0 = time.monotonic()
        with conn.transaction():
            conn.execute(f.read_text(encoding="utf-8"))
            conn.execute(
                "INSERT INTO schema_migrations(version,checksum,duration_ms,applied_by) "
                "VALUES (%s,%s,%s,%s)",
                (ver, digest, int((time.monotonic()-t0)*1000), applied_by))
        executed.append(ver)
    return executed
```
接线三处：
1. **启动**：main.py lifespan 里 create_all 之后调用 `run_pending(..., applied_by='startup')`（幂等，已执行秒过）。memory 三表类事故从此绝迹——ORM 新表要么进 SQL 脚本，要么 create_all 兜底后**补一条登记**。
2. **部署**：push_update.py 把"手工插播 3 条 SQL"段替换为 `python scripts/execute_core_sql.py --all-pending`，新环境/存量环境同一条命令收敛。
3. **存量库收编**：首次运行前，把已在生产执行过的 48 个脚本按历史报告批量登记（写一个 `--baseline` 模式：只登记不执行，checksum 取当前文件）。⚠️ 登记前逐个核对报告确认已执行，拿不准的脚本靠幂等性重跑一遍再登记。

守卫测试 `tests/test_schema_ledger.py`：
- 空库 → run_pending 全量 → 再 run_pending 应为 0 条（幂等）
- 修改任一已登记脚本内容 → 运行器必须中止
- `Base.metadata` 的表集合 ⊆ 实际库表集合（create_all 与 SQL 一致性）

### 3.2 视图只读守卫（S）

- `tests/test_view_readonly.py`：列出库中全部视图（`information_schema.views`），断言 ORM 映射类对应的 `__table__` 不在视图集合中；历史豁免（KaoyanSubject 等）显式白名单 + 整改待办。

**年度归档**：
```sql
-- 归档表（同结构，无 FK，按年分区可选）
CREATE TABLE kaoyan_scorelines_archive (LIKE kaoyan_scorelines INCLUDING ALL);
-- 每年 1 月归档 3 年前数据（示例：2027-01 归档 year<=2023）
WITH moved AS (
  DELETE FROM kaoyan_scorelines WHERE year <= 2023
  RETURNING *)
INSERT INTO kaoyan_scorelines_archive SELECT * FROM moved;
```
- 归档脚本进 `scripts/migrations/`，cron 每年触发，执行前 pg_dump 该表。
- 行数告警：`/api/health` 的 kb 快照或 diagnostics 增加 `scorelines_rows > 300000 → warn`。
- 前端查询默认只查主表；"历年全量"入口显式 UNION 归档表（慢查询加缓存，沿用院校列表 60s TTL 经验）。

### 3.5 恢复演练（S，每季度）

```bash
# 服务器或本机临时库
openssl enc -d -aes-256-cbc -pbkdf2 -in kaoyan_<ts>.dump.enc -out restore.dump -pass "pass:$KAOYAN_SECRET_KEY"
createdb kaoyan_restore_drill
pg_restore -h 127.0.0.1 -U kaoyan -d kaoyan_restore_drill --no-owner restore.dump

# 与生产行数对比（允许备份时点差），写演练报告 docs/reports/restore-drill-<date>.md

```
